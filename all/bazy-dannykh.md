## 1. Виды баз данных: реляционные, сетевые, иерархические. Примеры   
### Конкретика для ответа   
**База данных** — это именованная, структурированная и долговременно хранимая совокупность взаимосвязанных данных, предназначенная для многократного использования прикладными программами и пользователями. **Модель данных** — это способ описания структуры данных, допустимых связей между ними и операций над ними. Поэтому вопрос о видах БД надо раскрывать не как список названий, а как различие способов организации информации.   
**Иерархическая модель** — модель, в которой записи организованы в дерево: у каждой дочерней записи существует не более одного непосредственного родителя. Формальный признак: связь между типами записей обычно имеет вид `1:N`, а путь доступа к объекту задаётся маршрутом от корня дерева. Конкретный пример: база предприятия `Компания → Отдел → Сотрудник`. Запись сотрудника находится внутри отдела, отдел находится внутри компании. Если сотрудник одновременно участвует в нескольких проектах, иерархия начинает ломаться, потому что один объект приходится дублировать в разных ветвях.   
**Сетевая модель** — модель, в которой запись может участвовать в нескольких связях и иметь несколько «родителей». Формальный признак: поддерживаются связи `M:N` без обязательного сведения всей структуры к дереву. Пример: `Студент ↔ Дисциплина`, где студент изучает много дисциплин, а дисциплина изучается многими студентами. В сетевой модели такая связь естественна, но программы часто зависят от конкретных путей перехода между записями.   
**Реляционная модель** — модель, в которой данные представлены в виде отношений. В реализации СУБД отношение обычно выглядит как таблица: строки являются кортежами, столбцы — атрибутами, связи задаются первичными и внешними ключами. Пример: таблица `students(student\_id, full\_name, group\_id)` и таблица `groups(group\_id, group\_name)`. Значение `students.group\_id` ссылается на `groups.group\_id`, поэтому принадлежность студента группе задаётся не вложенностью, а совпадением значений ключей.   
Экзаменационный пример можно оформить так:   
|                  Предметная область   <br> |                                                      Иерархически   <br> |                                                                                        Сетево   <br> |                                         Реляционно   <br> |
|:-------------------------------------------|:-------------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------|:----------------------------------------------------------|
|                     Учебный процесс   <br> |                                Вуз → факультет → группа → студент   <br> |                                             Студенты связаны с дисциплинами и преподавателями   <br> | `students`, `groups`, `disciplines`, `enrollments`   <br> |
|                      Каталог файлов   <br> |                                               Диск → папка → файл   <br> |                                                      Файл может иметь ярлыки и связи с тегами   <br> |           `files`, `folders`, `tags`, `file\_tags`   <br> |
|                             Продажи   <br> |                                          Компания → склад → товар   <br> |                                                          Поставщик связан со многими товарами   <br> |                  `suppliers`, `products`, `orders`   <br> |

Мини-SQL для реляционного примера:   
```
CREATE TABLE groups (
    group_id integer PRIMARY KEY,
    group_name text NOT NULL
);

CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
Главный вывод: иерархическая БД удобна для строгих деревьев, сетевая — для сложных навигационных связей, реляционная — для табличного представления данных с декларативными запросами и формальными ограничениями целостности.   
База данных представляет собой организованную совокупность данных, предназначенную для длительного хранения, поиска, изменения и совместного использования. Модель базы данных определяет, как именно представляются объекты предметной области и связи между ними. В классической теории обычно сравнивают иерархическую, сетевую и реляционную модели. Их удобно воспринимать как три уровня эволюции: дерево, сеть и таблицы. Дерево хорошо там, где структура подчинённая; сеть нужна, когда один объект участвует во множестве связей; реляционная модель отделяет логическое представление от физических путей доступа.   
Иерархическая база данных организует записи в виде дерева. Каждый дочерний объект имеет одного родителя, но родитель может иметь много потомков. Такой подход естественен для структур «один ко многим»: университет содержит факультеты, факультет содержит кафедры, кафедра содержит преподавателей. Достоинство иерархической модели — простая навигация по заранее известному пути и высокая скорость доступа при стабильной структуре. Недостаток — слабая поддержка связей «многие ко многим». Если студент посещает дисциплины разных кафедр, участвует в проектах и относится к нескольким классификациям, дерево начинает требовать дублирования или искусственных обходных ссылок.   
```
graph TD
    U[Университет] --> F1[Факультет ИТ]
    F1 --> K1[Кафедра БД]
    K1 --> T1[Преподаватель]
    U --> F2[Экономический факультет]

```
Сетевая база данных расширяет иерархическую модель: запись может иметь несколько связей с другими записями. Она лучше подходит для отношений «многие ко многим»: студенты изучают много дисциплин, дисциплина изучается многими студентами; поставщики поставляют много товаров, один товар поставляется несколькими поставщиками. Сетевая модель выразительнее дерева, но часто требует навигационного доступа. Программа должна знать маршруты перехода между записями, поэтому логика приложения сильнее зависит от структуры хранения.   
```
graph LR
    S1[Студент Иванов] --> D1[Базы данных]
    S1 --> D2[SQL]
    S2[Студент Петров] --> D1
    D1 --> P1[Преподаватель Сидоров]

```
Реляционная база данных представляет данные в виде отношений, которые в СУБД отображаются как таблицы. Строки соответствуют кортежам, столбцы — атрибутам, связи задаются значениями ключей. Например, таблица `students` хранит студентов, таблица `groups` хранит группы, а поле `students.group\_id` ссылается на `groups.group\_id`. Пользователь описывает не путь обхода записей, а требуемый результат: `SELECT full\_name FROM students WHERE group\_id = 101`. СУБД сама выбирает план выполнения, индексы и методы доступа.   
```
erDiagram
    GROUPS ||--o{ STUDENTS : contains
    GROUPS { int group_id PK string name }
    STUDENTS { int student_id PK string full_name int group_id FK }

```
Примеры реляционных СУБД: PostgreSQL, MySQL, MariaDB, Oracle Database, Microsoft SQL Server, SQLite. SQLite при этом является встроенной SQL-СУБД: она хранит базу в файле и не требует отдельного серверного процесса. Реляционная модель стала основной благодаря строгой математической базе, нормализации, ключам, ограничениям целостности, транзакциям и SQL. На экзамене важно подчеркнуть: иерархическая модель удобна для дерева, сетевая — для сложной навигационной структуры, реляционная — для декларативной работы с таблицами и логическими связями.

## 2. Трехуровневая система организации базы данных ANSI. Логическая и физическая независимость данных   
### Конкретика для ответа   
**Трёхуровневая архитектура ANSI/SPARC** — это архитектурная модель организации БД, в которой описание данных делится на три уровня: внешний, концептуальный и внутренний. Она нужна для обеспечения независимости данных, то есть возможности изменять один уровень без обязательного изменения других уровней.   
**Внешний уровень** — совокупность пользовательских представлений данных. Он отвечает на вопрос: «Какие данные видит конкретный пользователь или приложение?». Например, преподаватель видит представление `student\_marks`, бухгалтер — `student\_contracts`, администратор — `users\_and\_roles`. Внешний уровень может скрывать конфиденциальные поля, объединять таблицы и показывать данные в удобном виде.   
**Концептуальный уровень** — единая логическая схема всей базы данных. Он отвечает на вопрос: «Какие сущности, атрибуты, связи и ограничения существуют в предметной области?». Например: есть сущности `Студент`, `Группа`, `Дисциплина`, `Оценка`; студент принадлежит одной группе; оценка относится к одному студенту и одной дисциплине.   
**Внутренний уровень** — физическое представление данных в памяти компьютера. Он отвечает на вопрос: «Как данные реально размещены и как к ним осуществляется доступ?». Здесь находятся файлы данных, страницы, индексы, методы хранения, кластеры, партиции, буферы.   
```
graph TD
    E1[Внешняя схема преподавателя: оценки] --> C[Концептуальная схема БД]
    E2[Внешняя схема бухгалтерии: договоры] --> C
    E3[Внешняя схема администратора: пользователи] --> C
    C --> I[Внутренняя схема: файлы, страницы, индексы]

```
**Логическая независимость данных** — возможность изменить концептуальную схему без изменения внешних схем и прикладных программ, если их представление данных сохранено. Пример: таблицу `students` разделили на `persons` и `students`, но сохранили представление `student\_view`. Приложение продолжает выполнять `SELECT \* FROM student\_view`, хотя внутренняя логическая структура изменилась.   
**Физическая независимость данных** — возможность изменить внутреннее хранение без изменения концептуальной схемы и запросов пользователей. Пример: добавили индекс на `students(group\_id)`, перенесли таблицу в другой tablespace, изменили способ хранения или включили партиционирование. Запрос `SELECT \* FROM students WHERE group\_id = 101` остался тем же.   
SQL-пример внешнего представления:   
```
CREATE VIEW student_progress AS
SELECT s.student_id, s.full_name, d.name AS discipline, m.mark
FROM students s
JOIN marks m ON m.student_id = s.student_id
JOIN disciplines d ON d.discipline_id = m.discipline_id;

```
Если позднее таблица `marks` будет физически индексирована или логически разделена, но представление `student\_progress` останется совместимым, прикладной код можно не менять. Это и есть практический смысл трёхуровневой архитектуры.   
Трёхуровневая архитектура ANSI/SPARC описывает базу данных через внешний, концептуальный и внутренний уровни. Её задача — разделить пользовательские представления, общую логическую схему и физическое хранение. Такое разделение защищает приложения от изменений реализации и позволяет разным пользователям работать с одной базой через разные представления.   
Внешний уровень — это уровень отдельных пользователей и приложений. Бухгалтер видит договоры и оплаты, преподаватель видит студентов и оценки, администратор видит пользователей и права. В SQL внешние представления часто реализуются через `VIEW`. Представление может объединять несколько таблиц и скрывать лишние поля. Например, `student\_progress` может показывать ФИО студента, дисциплину и оценку, хотя физически данные лежат в таблицах студентов, дисциплин и ведомостей.   
Концептуальный уровень описывает единую логическую схему всей базы: сущности, атрибуты, связи, ключи, ограничения целостности и правила предметной области. Для учебной базы это сущности «Студент», «Группа», «Дисциплина», «Преподаватель», «Оценка». На этом уровне важно, что студент принадлежит группе, оценка относится к студенту и дисциплине, группа имеет уникальный номер. Концептуальная схема не должна зависеть от того, на каком диске лежат файлы и какие индексы созданы.   
Внутренний уровень описывает физическое хранение: файлы, страницы, индексы, методы доступа, журналы транзакций, буферизацию, партиционирование. Например, таблица заказов может храниться по разделам за разные годы, иметь B-tree индекс по дате и отдельный индекс по клиенту. Пользователь при этом продолжает работать с таблицей `orders`, не зная деталей размещения.   
```
graph TD
    E[Внешний уровень: представления пользователей] --> C[Концептуальный уровень: логическая схема]
    C --> I[Внутренний уровень: файлы, страницы, индексы]
    U1[Преподаватель] --> E
    U2[Бухгалтер] --> E
    U3[Администратор] --> E

```
Физическая независимость данных означает, что изменения внутреннего уровня не требуют изменения логической схемы и программ. Можно создать индекс, перенести таблицу на другой диск, изменить параметры хранения или выполнить кластеризацию. Запрос `SELECT \* FROM students WHERE group\_id = 101` остаётся тем же, хотя СУБД после добавления индекса выполнит его быстрее.   
Логическая независимость данных означает возможность изменять концептуальную схему без обязательного изменения внешних представлений. Например, таблицу `students` можно разделить на `persons` и `student\_profiles`, а для старого приложения оставить представление `students`. Логическая независимость сложнее физической, потому что изменения логики затрагивают смысл данных. Тем не менее представления, совместимые миграции и API помогают сохранить старые интерфейсы.   
Пример физической независимости: добавлен индекс `CREATE INDEX idx\_students\_group ON students(group\_id);`, но приложение не изменилось. Пример логической независимости: адрес студента вынесен из таблицы студентов в `student\_addresses`, а старый отчёт получает прежний вид через `VIEW`. Главная идея ANSI-архитектуры: пользователь работает с логической моделью, а детали хранения и часть изменений схемы скрываются за слоями абстракции.

## 3. Основные требования к системе управления базами данных   
### Конкретика для ответа   
**Система управления базами данных (СУБД)** — это программная система, предназначенная для определения структуры базы данных, хранения, поиска, изменения, защиты данных и управления одновременным доступом пользователей. Требования к СУБД удобно раскрывать через конкретные функции, которые она обязана выполнять.   
1. **Определение данных.** СУБД должна позволять создавать структуры хранения: таблицы, представления, индексы, ограничения, схемы. В SQL это реализуется командами DDL: `CREATE TABLE`, `ALTER TABLE`, `DROP INDEX`.   
2. **Манипулирование данными.** СУБД должна обеспечивать добавление, изменение, удаление и выборку данных. В SQL это `INSERT`, `UPDATE`, `DELETE`, `SELECT`. Пример: `UPDATE accounts SET balance = balance - 100 WHERE account\_id = 1`.   
3. **Целостность данных.** СУБД должна не просто хранить значения, а не допускать противоречивых состояний. Для этого применяются `PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `NOT NULL`, `CHECK`. Например, оценка студента не должна быть равна 99, если допустимы значения от 2 до 5.   
4. **Транзакционность.** СУБД должна поддерживать ACID-свойства: атомарность, согласованность, изолированность и долговечность. Денежный перевод должен либо полностью списать и зачислить сумму, либо не выполнить ни одного действия.   
5. **Многопользовательский доступ.** СУБД должна корректно работать, когда несколько пользователей одновременно читают и изменяют данные. Для этого используются блокировки, MVCC, уровни изоляции транзакций.   
6. **Безопасность.** СУБД должна разграничивать права доступа: кто может читать, кто может изменять, кто может создавать таблицы, кто может выдавать права. Пример: аналитик имеет `SELECT`, но не имеет `DELETE`.   
7. **Восстановление после сбоев.** СУБД должна сохранять данные при отказах питания, ошибках приложений и сбоях сервера. Для этого используются журнал транзакций, резервное копирование, контрольные точки, восстановление из WAL.   
8. **Эффективность доступа.** СУБД должна обеспечивать приемлемое время ответа за счёт оптимизатора запросов, индексов, статистики, кэширования и выбора плана выполнения.   
9. **Независимость данных.** Пользователь должен работать с логической схемой, а не с физическими файлами. Добавление индекса не должно требовать переписывания всех запросов.

|:--------------------------------------------|:--------------------------------------------|:----------------------------------------------------------------------------------------------|

На экзамене важно не перечислять требования сухим списком, а показать, что СУБД является посредником между пользователем и физическими данными: она управляет структурой, доступом, согласованностью, безопасностью и восстановлением.   
СУБД — программный комплекс, который создаёт, хранит, изменяет, защищает и предоставляет данные пользователям и приложениям. Основные требования к СУБД вытекают из того, что база данных обычно является общим, долговременным и критически важным ресурсом. СУБД должна не просто записывать строки, а обеспечивать корректность, независимость, безопасность, многопользовательскую работу и восстановление после сбоев.   
Первое требование — поддержка модели данных и средств описания структуры. Реляционная СУБД должна позволять создавать таблицы, атрибуты, типы, ключи, связи, индексы, представления и ограничения. Для этого используются команды DDL: `CREATE`, `ALTER`, `DROP`. Структура должна храниться в системном каталоге, чтобы СУБД могла проверять операции и чтобы пользователи могли получать метаданные.   
Второе требование — обеспечение целостности. СУБД должна контролировать первичные ключи, внешние ключи, уникальность, обязательность значений, доменные ограничения и бизнес-правила. Если задан внешний ключ, нельзя вставить студента в несуществующую группу. Если задано `CHECK (grade BETWEEN 2 AND 5)`, нельзя поставить оценку 9. Ограничения должны работать независимо от приложения, потому что к базе могут подключаться разные клиенты.   
Третье требование — независимость данных. Пользователь и приложение должны работать с логической схемой, а не с физическими адресами и файлами. Добавление индекса, изменение способа хранения или перенос таблицы не должны ломать запросы. Это снижает стоимость сопровождения и позволяет администратору оптимизировать систему без переписывания бизнес-логики.   
Четвёртое требование — эффективная обработка запросов. СУБД должна иметь оптимизатор, статистику, индексы, буферизацию и методы доступа. Запросы соединения, группировки, сортировки и фильтрации должны выполняться с приемлемой скоростью. Индекс ускоряет поиск, но СУБД сама решает, когда его выгодно использовать.   
Пятое требование — транзакционность и восстановление. Транзакции должны обладать свойствами ACID: атомарностью, согласованностью, изолированностью и долговечностью. Если перевод денег состоит из списания и зачисления, обе операции должны выполниться вместе или вместе отмениться. Журналы транзакций и контрольные точки позволяют восстановить базу после сбоя.   
Шестое требование — многопользовательский доступ. СУБД должна корректно обслуживать параллельные транзакции, предотвращать потерянные обновления, грязные чтения и другие аномалии. Для этого используются блокировки, MVCC и уровни изоляции.   
Седьмое требование — безопасность. СУБД должна поддерживать аутентификацию, роли, права, `GRANT`, `REVOKE`, аудит, шифрование соединений и резервных копий. Пользователь должен получать только необходимые права, а не полный доступ ко всем таблицам.   
Восьмое требование — администрирование: резервное копирование, восстановление, мониторинг, анализ планов запросов, миграции схемы, репликация, журналирование. Хорошая СУБД должна обслуживать полный жизненный цикл данных, а не только текущий запрос.   
```
graph TD
    DBMS[Требования к СУБД] --> M[Модель и язык данных]
    DBMS --> I[Целостность]
    DBMS --> P[Производительность]
    DBMS --> T[Транзакции]
    DBMS --> S[Безопасность]
    DBMS --> A[Администрирование]

```
Итак, СУБД должна быть одновременно хранилищем, контролёром правил, диспетчером параллельной работы, механизмом восстановления и охранной системой. Без этих требований база быстро превращается в файл с таблицами, а не в управляемую информационную систему.

## 4. Терминология реляционных баз данных: отношение, сущность, атрибуты, домен, ключ   
### Конкретика для ответа   
**Отношение** в реляционной модели — это множество кортежей одинаковой структуры. В практической SQL-СУБД отношение обычно соответствует таблице. Например, `students(student\_id, full\_name, birth\_date, group\_id)` — отношение, описывающее студентов. Строка таблицы — это **кортеж**, а столбец — **атрибут**.   
**Сущность** — объект предметной области, о котором нужно хранить данные. Сущностью может быть студент, преподаватель, группа, заказ, товар, дисциплина. Важно различать сущность и отношение: сущность относится к предметной области, а отношение является способом её логического представления в БД.   
**Атрибут** — именованное свойство сущности или отношения. Например, у сущности `Студент` атрибутами являются `student\_id`, `full\_name`, `birth\_date`, `group\_id`. Атрибут имеет имя, тип данных и множество допустимых значений.   
**Домен** — множество допустимых значений атрибута. Например, домен атрибута `mark` может быть `{2, 3, 4, 5}`, домен `birth\_date` — множество корректных календарных дат, домен `email` — строки определённого формата. В SQL домен частично задаётся типом данных и ограничениями: `integer CHECK (mark BETWEEN 2 AND 5)`.   
**Ключ** — атрибут или набор атрибутов, позволяющий однозначно идентифицировать кортеж отношения. **Суперключ** однозначно идентифицирует строку, но может содержать лишние атрибуты. **Потенциальный ключ** минимален: из него нельзя удалить атрибут без потери уникальности. **Первичный ключ** — выбранный потенциальный ключ. **Внешний ключ** — атрибут, значения которого ссылаются на первичный или уникальный ключ другого отношения.   
Пример:   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    email text UNIQUE,
    group_id integer REFERENCES groups(group_id),
    mark integer CHECK (mark BETWEEN 2 AND 5)
);

```
В этом примере:   
|                        Термин   <br> |                                          Конкретный элемент   <br> |
|:-------------------------------------|:-------------------------------------------------------------------|
|                     Отношение   <br> |                                                  `students`   <br> |
|                        Кортеж   <br> |                               одна строка таблицы студентов   <br> |
|                       Атрибут   <br> |                          `full\_name`, `email`, `group\_id`   <br> |
|                         Домен   <br> |                       допустимые значения `mark`: от 2 до 5   <br> |
|                Первичный ключ   <br> |                                               `student\_id`   <br> |
|                  Внешний ключ   <br> |                                                 `group\_id`   <br> |
|               Уникальный ключ   <br> |                                                     `email`   <br> |

Схема связи:   
```
erDiagram
    GROUPS ||--o{ STUDENTS : includes
    GROUPS { int group_id PK string group_name }
    STUDENTS { int student_id PK string full_name string email UK int group_id FK }

```
Формулировка для экзамена: реляционная терминология связывает предметную область и формальную модель. Сущность описывает объект реального мира, отношение задаёт табличную структуру, атрибут описывает свойство, домен ограничивает допустимые значения, а ключи обеспечивают идентификацию строк и связи между таблицами.   
Реляционная модель опирается на строгую терминологию. Отношение — это математическая структура, которая в практической СУБД обычно представляется таблицей. Отношение имеет заголовок, где перечислены атрибуты и их домены, и тело, состоящее из кортежей. В SQL кортеж соответствует строке, атрибут — столбцу, домен — допустимому множеству значений.   
Сущность — объект предметной области, о котором требуется хранить данные: студент, группа, дисциплина, заказ, товар, клиент. Сущность имеет свойства, которые в реляционной схеме становятся атрибутами. Например, сущность «Студент» имеет `student\_id`, `full\_name`, `birth\_date`, `group\_id`.   
Атрибут — именованная характеристика сущности или отношения. Домен задаёт допустимые значения атрибута. Для `birth\_date` доменом являются даты, для `grade` — числа от 2 до 5, для `email` — строки определённого формата. Домен шире, чем технический тип: тип `integer` допускает много чисел, но домен «оценка» ограничивает их до 2, 3, 4, 5.   
Ключ — атрибут или набор атрибутов, идентифицирующий строки. Потенциальный ключ минимально уникален. Первичный ключ выбирается как основной идентификатор. Внешний ключ ссылается на ключ другой таблицы и задаёт связь между отношениями. Составной ключ состоит из нескольких атрибутов, например `(student\_id, discipline\_id)` в таблице результатов.   
```
CREATE TABLE groups (
    group_id integer PRIMARY KEY,
    group_name text NOT NULL UNIQUE
);
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
```

    GROUPS ||--o{ STUDENTS : contains
    GROUPS { int group_id PK string group_name }
    STUDENTS { int student_id PK string full_name int group_id FK }

```
Пример отношения `STUDENTS`:   
| student\_id   <br> |               full\_name   <br> | birth\_date   <br> | group\_id   <br> |
|:-------------------|:--------------------------------|:-------------------|:-----------------|
|           1   <br> |             Иванов И. И.   <br> |  2004-03-10   <br> |       101   <br> |
|           2   <br> |             Петров П. П.   <br> |  2003-11-02   <br> |       101   <br> |
|           3   <br> |           Сидорова А. В.   <br> |  2004-07-22   <br> |       102   <br> |

Здесь `STUDENTS` — отношение, строки — кортежи, `student\_id`, `full\_name`, `birth\_date`, `group\_id` — атрибуты, `student\_id` — первичный ключ, `group\_id` — внешний ключ. На экзамене важно показать связь понятий: сущность предметной области описывается атрибутами; атрибуты имеют домены; множество однотипных сущностей хранится как отношение; ключи обеспечивают идентификацию и связи.

## 5. Правила реляционной модели: с нулевого по пятое правило   
### Конкретика для ответа   
Правила Кодда формулируют требования к настоящей реляционной СУБД. Нулевое правило задаёт общий критерий, а правила 1–5 раскрывают базовые свойства реляционного представления, доступа и обработки неопределённых значений.   
**Правило 0. Основное правило.** Система считается реляционной СУБД только тогда, когда она управляет базой данных исключительно с помощью реляционных возможностей. Иначе говоря, таблицы, ключи, ограничения и операции над отношениями должны быть не внешней оболочкой, а основой системы. Если продукт показывает данные в таблицах, но требует навигации по физическим указателям, это ещё не полноценная реляционная СУБД.   
**Правило 1. Информационное правило.** Вся информация в реляционной БД должна быть представлена только в виде значений в таблицах. Это относится и к пользовательским данным, и к метаданным. Пример: имя студента, номер группы, оценка, название таблицы и описание столбца должны быть представлены как значения, доступные через табличные структуры.   
**Правило 2. Гарантированный доступ.** Каждое атомарное значение должно быть доступно по имени таблицы, значению первичного ключа строки и имени столбца. Например, оценку студента Иванова по дисциплине можно получить, зная таблицу, идентификатор строки и атрибут `mark`. Это исключает зависимость от физического адреса записи в файле.   
**Правило 3. Систематическая обработка NULL.** СУБД должна поддерживать специальное значение `NULL` для отсутствующих или неизвестных данных. `NULL` не равен нулю и не равен пустой строке. Пример: если дата отчисления студента неизвестна или студент не отчислен, поле `expelled\_at` может быть `NULL`. В SQL выражение `expelled\_at = NULL` неверно, надо писать `expelled\_at IS NULL`.   
**Правило 4. Активный реляционный каталог.** Описание структуры базы данных должно храниться в самой базе в виде таблиц системного каталога и быть доступно реляционными средствами. Например, в PostgreSQL сведения о таблицах и столбцах можно получать через `information\_schema.tables` и `information\_schema.columns`.   
```
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public';

```
**Правило 5. Исчерпывающий подъязык данных.** СУБД должна иметь язык, который поддерживает определение данных, выборку, изменение, ограничения целостности, представления, транзакции и права доступа. В современных СУБД эту роль выполняет SQL: `CREATE TABLE`, `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `COMMIT`, `GRANT`.   
Краткая таблица для запоминания:   
|        Правило   <br> |                                                                 Смысл   <br> |                                                                Пример   <br> |
|:----------------------|:-----------------------------------------------------------------------------|:-----------------------------------------------------------------------------|
|              0   <br> |                                  Система управляет данными реляционно   <br> |                                         не через физические указатели   <br> |
|              1   <br> |                                     Все данные представлены таблицами   <br> |                                  пользовательские данные и метаданные   <br> |
|              2   <br> |                                    Доступ по таблице, ключу и столбцу   <br> |                             `students` + `student\_id` + `full\_name`   <br> |
|              3   <br> |                                        `NULL` обрабатывается системно   <br> |                                         `IS NULL`, трёхзначная логика   <br> |
|              4   <br> |                                              Каталог тоже реляционный   <br> |                                                 `information\_schema`   <br> |
|              5   <br> |                                          Есть полноценный язык данных   <br> |                                               SQL как DDL/DML/DCL/TCL   <br> |

На экзамене важно не просто назвать правила, а показать, что они защищают пользователя от физической зависимости и делают базу данных логической табличной системой.   
Правила Кодда описывают идеальные требования к реляционной СУБД. Нулевое правило утверждает: система, называющая себя реляционной, должна управлять базой данных именно через реляционные возможности. Нельзя быть реляционной только на вывеске, а внутри требовать навигации по физическим указателям.   
Первое правило — правило информации. Вся информация в БД должна быть представлена на логическом уровне одним способом: значениями в таблицах. Это относится не только к пользовательским данным, но и к метаданным. В современных СУБД сведения о таблицах, столбцах, индексах и ограничениях доступны через системные каталоги и `information\_schema`.   
Второе правило — гарантированный доступ. Каждое атомарное значение должно быть доступно через имя таблицы, значение первичного ключа строки и имя столбца. Пользователь обращается к данным логически, а не через адрес страницы на диске.   
Третье правило — систематическая обработка неопределённых значений. СУБД должна поддерживать `NULL` как специальное значение для неизвестной, отсутствующей или неприменимой информации. `NULL` не равен нулю или пустой строке. В SQL для него используются `IS NULL` и трёхзначная логика.   
Четвёртое правило — активный динамический каталог на основе реляционной модели. Описание базы должно храниться как данные и быть доступно тем же языком, что и обычные таблицы. Это делает структуру БД управляемой и проверяемой.   
Пятое правило — полный подъязык данных. Реляционная СУБД должна иметь язык, который поддерживает определение данных, представления, манипулирование данными, ограничения целостности, авторизацию и транзакции. В современных системах эту роль выполняет SQL.   
```
graph TD
    R0[0. Реляционное управление] --> R1[1. Информация в таблицах]
    R1 --> R2[2. Гарантированный доступ]
    R1 --> R4[4. Реляционный каталог]
    R2 --> R3[3. NULL]
    R4 --> R5[5. Полный язык данных]

```
Смысл первых правил — сформировать фундамент: данные и метаданные должны быть представлены реляционно, доступ к значениям должен быть логическим, отсутствующие значения должны обрабатываться единообразно, а язык должен покрывать полный цикл работы с БД.

## 6. Правила реляционной модели: с шестого по двенадцатое правило   
### Конкретика для ответа   
Правила Кодда 6–12 продолжают идею: реляционная СУБД должна обеспечивать работу с представлениями, множественными операциями, независимостью данных и ограничениями целостности.   
**Правило 6. Обновляемость представлений.** Если представление теоретически может быть обновлено без неоднозначности, СУБД должна позволять его обновлять. Например, простое представление `active\_students`, построенное из одной таблицы `students`, может быть обновляемым. Но представление с группировкой `COUNT(\*)` обычно нельзя обновить напрямую, потому что непонятно, какие исходные строки надо изменить.   
```
CREATE VIEW active_students AS
SELECT student_id, full_name, group_id
FROM students
WHERE expelled_at IS NULL;

```
**Правило 7. Высокоуровневые операции вставки, обновления и удаления.** СУБД должна поддерживать операции над множествами строк, а не только построчную навигацию. Пример: `UPDATE students SET status = 'archived' WHERE graduated\_at < DATE '2025-01-01';` изменяет сразу множество записей.   
**Правило 8. Физическая независимость данных.** Изменение физического хранения не должно ломать приложения. Например, добавление индекса, изменение файловой организации или перенос таблицы в другой раздел диска не должны менять SQL-запросы.   
**Правило 9. Логическая независимость данных.** Изменение логической схемы не должно ломать приложения, если их внешнее представление можно сохранить. Например, таблицу `students` разделили на `persons` и `student\_profiles`, но создали представление `students\_old\_api`, совместимое со старым приложением.   
**Правило 10. Независимость ограничений целостности.** Ограничения должны задаваться на уровне БД и храниться в каталоге, а не быть зашитыми только в код приложения. Пример: `CHECK (mark BETWEEN 2 AND 5)` гарантирует корректность оценки независимо от того, из какого приложения пришла запись.   
**Правило 11. Независимость распределения.** Пользователь не должен зависеть от того, где физически расположены данные. Если часть таблиц находится на другом сервере или в другой партиции, логический запрос должен оставаться тем же, насколько это поддерживается СУБД.   
**Правило 12. Правило неподрыва.** Низкоуровневые средства доступа не должны позволять обходить ограничения реляционной модели. Если у СУБД есть специальные интерфейсы, они не должны давать возможность нарушить ключи, ограничения и целостность.   
Сводная таблица:   
|        Правило   <br> |                                                                                 Проверочный вопрос   <br> |                                                                     Пример   <br> |
|:----------------------|:----------------------------------------------------------------------------------------------------------|:----------------------------------------------------------------------------------|

|              7   <br> |                                                    Можно ли менять множество строк одной командой?   <br> |                                                     `UPDATE ... WHERE ...`   <br> |

|              9   <br> |                                              Не ломается ли внешний интерфейс при изменении схемы?   <br> |                                               сохранили совместимое `VIEW`   <br> |

Шестое правило Кодда — обновляемость представлений. Все представления, которые теоретически можно обновлять без неоднозначности, должны быть обновляемыми. Например, представление активных студентов на основе одной таблицы может поддерживать `UPDATE`, но агрегированное представление с `GROUP BY` обычно неоднозначно.   
Седьмое правило — высокоуровневые операции вставки, обновления и удаления. Реляционная система должна работать с множествами строк, а не заставлять программу изменять записи по одной. Команда `UPDATE orders SET status='archived' WHERE created\_at < '2024-01-01'` изменяет множество строк одной операцией.   
Восьмое правило — физическая независимость данных. Изменение индексов, файлов, страниц, размещения таблиц или параметров хранения не должно менять приложения. Девятое правило — логическая независимость данных. Изменения логической схемы, не разрушающие внешние представления, не должны ломать программы. Например, таблицу можно разделить на две, а старое приложение оставить работать через `VIEW`.   
Десятое правило — независимость целостности. Ограничения должны храниться в самой базе и задаваться языком данных, а не только кодом приложения. Одиннадцатое правило — независимость распределения: пользователь должен видеть единую логическую БД независимо от того, распределены данные физически или нет. Двенадцатое правило — запрет обхода: низкоуровневый интерфейс не должен позволять нарушать реляционные ограничения и права.

Эти правила защищают реляционную модель от возврата к построчной навигации, зависимости программ от хранения и размывания целостности. Они показывают, почему ограничения, представления, права и транзакции должны быть частью самой СУБД.

## 7. Операции реляционной алгебры: объединение, пересечение и разность   
### Конкретика для ответа   
Операции **объединения**, **пересечения** и **разности** относятся к теоретико-множественным операциям реляционной алгебры. Они применимы только к **совместимым по объединению отношениям**. Это значит, что у отношений одинаковое число атрибутов, а соответствующие атрибуты имеют совместимые домены. Например, можно объединять таблицы студентов дневной и заочной формы, если обе имеют столбцы `(student\_id, full\_name)`. Нельзя напрямую объединять `(student\_id, full\_name)` и `(discipline\_id, hours, semester)`.   
Пусть есть отношения:   
`A = students\_db`   
| student\_id   <br> |     full\_name   <br> |
|:-------------------|:----------------------|
|           1   <br> |         Иванов   <br> |
|           2   <br> |         Петров   <br> |
|           3   <br> |        Сидоров   <br> |

`B = students\_python`   
| student\_id   <br> |       full\_name   <br> |
|:-------------------|:------------------------|
|           2   <br> |           Петров   <br> |
|           3   <br> |          Сидоров   <br> |
|           4   <br> |         Смирнова   <br> |

**Объединение** `A ∪ B` возвращает все кортежи, которые входят хотя бы в одно из отношений. Дубликаты в классической реляционной алгебре устраняются.   
| student\_id   <br> |       full\_name   <br> |
|:-------------------|:------------------------|
|           1   <br> |           Иванов   <br> |
|           2   <br> |           Петров   <br> |
|           3   <br> |          Сидоров   <br> |
|           4   <br> |         Смирнова   <br> |

SQL-аналог:   
```
SELECT student_id, full_name FROM students_db
UNION
SELECT student_id, full_name FROM students_python;

```
**Пересечение** `A ∩ B` возвращает кортежи, которые входят одновременно в оба отношения.   
| student\_id   <br> |     full\_name   <br> |
|:-------------------|:----------------------|
|           2   <br> |         Петров   <br> |
|           3   <br> |        Сидоров   <br> |

SQL-аналог:   
```
SELECT student_id, full_name FROM students_db
INTERSECT
SELECT student_id, full_name FROM students_python;

```
**Разность** `A − B` возвращает кортежи, которые входят в `A`, но не входят в `B`.   
| student\_id   <br> |   full\_name   <br> |
|:-------------------|:--------------------|
|           1   <br> |       Иванов   <br> |

SQL-аналог:   
```
SELECT student_id, full_name FROM students_db
EXCEPT
SELECT student_id, full_name FROM students_python;

```
Диаграммы Венна можно описать так:   
```
flowchart LR
    U[Объединение A ∪ B: вся область A и B]
    I[Пересечение A ∩ B: только общая часть]
    D[Разность A - B: часть A вне B]

```
Важная экзаменационная деталь: `A − B` и `B − A` обычно дают разные результаты, то есть разность некоммутативна. Объединение и пересечение коммутативны: `A ∪ B = B ∪ A`, `A ∩ B = B ∩ A`. Практический смысл операций: объединение собирает данные из нескольких источников, пересечение ищет общие элементы, разность выявляет отсутствующие или несовпадающие записи.   
Реляционная алгебра — формальный язык операций над отношениями. Объединение, пересечение и разность относятся к операциям над множествами. Они применимы только к совместимым отношениям: у них должно быть одинаковое количество атрибутов и совместимые домены соответствующих столбцов.   
Объединение `R ∪ S` возвращает все кортежи, которые есть хотя бы в одном отношении. В классической алгебре дубликаты не сохраняются. В SQL аналог — `UNION`, а `UNION ALL` сохраняет повторы.   
```
R ∪ S = { t | t ∈ R или t ∈ S }

```
Пересечение `R ∩ S` возвращает только кортежи, присутствующие одновременно в `R` и `S`.   
```
R ∩ S = { t | t ∈ R и t ∈ S }

```
Разность `R − S` возвращает кортежи, которые есть в `R`, но отсутствуют в `S`. Порядок важен: `R − S` не равно `S − R`.   
```
R − S = { t | t ∈ R и t ∉ S }

```
Пусть `R` — студенты курса «Базы данных», `S` — студенты курса «SQL».   
`R`:   
| id   <br> |             name   <br> |
|:----------|:------------------------|
|  1   <br> |           Иванов   <br> |
|  2   <br> |           Петров   <br> |
|  3   <br> |         Сидорова   <br> |

`S`:   
| id   <br> |               name   <br> |
|:----------|:--------------------------|
|  2   <br> |             Петров   <br> |
|  3   <br> |           Сидорова   <br> |
|  4   <br> |          Кузнецова   <br> |

`R ∪ S` даёт Иванова, Петрова, Сидорову, Кузнецову. `R ∩ S` даёт Петрова и Сидорову. `R − S` даёт Иванова. `S − R` даёт Кузнецову.   
```
SELECT id, name FROM database_course
UNION
SELECT id, name FROM sql_course;

SELECT id, name FROM database_course
INTERSECT
SELECT id, name FROM sql_course;

SELECT id, name FROM database_course
EXCEPT
SELECT id, name FROM sql_course;

```
Диаграммы Венна: объединение закрашивает оба круга, пересечение — общую часть, разность — часть первого круга вне второго.   
```
Объединение: R + S целиком
Пересечение: только R ∩ S
Разность: только R без области S

```
Практически эти операции применяются для объединения списков клиентов, поиска общих участников, поиска отсутствующих элементов, сверки данных между системами. Важно проверять не только техническую совместимость столбцов, но и смысловую: объединять `student\_id, name` со `teacher\_id, name` можно технически, но результат уже будет множеством персон, а не студентов.

## 8. Классификация СУБД по архитектуре: встроенные, файл-серверные, клиент-серверные   
### Конкретика для ответа   
Классификация СУБД по архитектуре показывает, где выполняется обработка данных и как приложения получают доступ к хранилищу. Основные варианты: встроенная СУБД, файл-серверная архитектура и клиент-серверная архитектура.   
**Встроенная СУБД** — СУБД, работающая внутри процесса приложения и не требующая отдельного серверного процесса. Пример: SQLite. База обычно хранится в одном файле, а библиотека SQLite подключается к приложению. Приложение вызывает функции библиотеки, а не отправляет запросы отдельному серверу.   
```
flowchart LR
    A[Приложение] --> L[Библиотека SQLite]
    L --> F[(Файл базы данных .sqlite)]

```
Плюсы: простота установки, отсутствие администрирования сервера, удобство для мобильных приложений, локальных программ и небольших систем. Минусы: ограниченная масштабируемость для большого числа сетевых пользователей, сложнее централизовать доступ и разграничение прав.   
**Файл-серверная архитектура** — архитектура, при которой файлы БД лежат на файловом сервере, а значительная часть обработки выполняется на клиентских машинах. Клиент получает доступ к файлам по сети. Примерная логика: приложение открывает файл базы, читает нужные блоки и само выполняет часть операций.   
```
flowchart LR
    C1[Клиент 1] --> FS[(Файловый сервер: файлы БД)]
    C2[Клиент 2] --> FS
    C3[Клиент 3] --> FS

```
Плюсы: простая организация для малых локальных сетей. Минусы: большой сетевой трафик, повышенный риск повреждения файлов при сбоях, слабая централизованная обработка запросов, проблемы при одновременной работе большого числа пользователей.   
**Клиент-серверная СУБД** — архитектура, при которой приложение-клиент отправляет запросы серверу БД, а сервер выполняет запрос, управляет транзакциями, индексами, блокировками, журналом и правами доступа. Примеры: PostgreSQL, MySQL, MariaDB, Oracle Database, Microsoft SQL Server.   
```
flowchart LR
    C1[Клиентское приложение] --> DB[Сервер СУБД]
    C2[Веб-приложение] --> DB
    C3[Админ-клиент] --> DB
    DB --> S[(Файлы данных, WAL, индексы)]

```
Конкретное сравнение:   
|               Архитектура   <br> |                                        Где выполняется SQL/обработка   <br> |                                Примеры   <br> |                                                 Когда использовать   <br> |
|:---------------------------------|:----------------------------------------------------------------------------|:----------------------------------------------|:--------------------------------------------------------------------------|
|                Встроенная   <br> |                                                    внутри приложения   <br> |                                 SQLite   <br> |                                мобильное приложение, локальный кэш   <br> |
|               Файл-сервер   <br> |                                частично на клиенте, файлы на сервере   <br> |                   старые настольные БД   <br> |                                               малая локальная сеть   <br> |
|             Клиент-сервер   <br> |                                                      на сервере СУБД   <br> |                      PostgreSQL, MySQL   <br> |                                      многопользовательские системы   <br> |

Экзаменационный вывод: чем больше пользователей, транзакций и требований к безопасности, тем важнее клиент-серверная архитектура. Встроенные СУБД удобны для локального хранения, а файл-серверная архитектура исторически проста, но хуже подходит для современных нагруженных систем.   
По архитектуре СУБД делятся на встроенные, файл-серверные и клиент-серверные. Архитектура определяет, где находится ядро СУБД, кто выполняет запросы и как приложение взаимодействует с данными.   
Встроенная СУБД включается в приложение как библиотека. Нет отдельного серверного процесса: приложение само открывает файл базы и вызывает функции движка. Пример — SQLite. Такая архитектура удобна для мобильных приложений, локальных кэшей, настольных программ, тестов. Достоинства: простота, один файл, малые накладные расходы. Недостатки: ограниченная многопользовательская работа и слабая пригодность для больших серверных систем.   
```
graph LR
    A[Приложение] --> B[Библиотека СУБД]
    B --> C[(Файл БД)]

```
Файл-серверная архитектура хранит файлы базы на сетевом файловом сервере, а обработка во многом выполняется на клиентах. Это просто, но плохо масштабируется: по сети могут передаваться большие объёмы данных, сложнее контролировать блокировки и безопасность, выше риск повреждения общего файла.   
```
graph TD
    FS[(Файловый сервер)]
    C1[Клиент 1] --> FS
    C2[Клиент 2] --> FS
    C3[Клиент 3] --> FS

```
Клиент-серверная СУБД имеет отдельный сервер, который выполняет SQL-запросы, управляет файлами, индексами, правами, транзакциями и восстановлением. Клиенты отправляют запросы и получают результаты, не читая файлы напрямую. Примеры: PostgreSQL, MySQL, Oracle, SQL Server. Такая архитектура подходит для многопользовательских приложений, потому что контроль сосредоточен на сервере.   
```
graph LR
    C1[Клиент] --> S[Сервер СУБД]
    C2[Клиент] --> S
    S --> D[(Данные, индексы, журнал)]

```
|                     Архитектура   <br> |           Примеры   <br> |                                                    Плюсы   <br> |                                                               Минусы   <br> |
|:---------------------------------------|:-------------------------|:----------------------------------------------------------------|:----------------------------------------------------------------------------|
|                      Встроенная   <br> |            SQLite   <br> |                                 просто, локально, быстро   <br> |                                    ограничена для серверных нагрузок   <br> |
|                  Файл-серверная   <br> |    shared-file БД   <br> |                            простое хранение общего файла   <br> |                                       сеть, блокировки, безопасность   <br> |
|                Клиент-серверная   <br> | PostgreSQL, MySQL   <br> |                           транзакции, права, оптимизация   <br> |                                  требуется администрирование сервера   <br> |

Если нужно хранить заметки в мобильном приложении, подойдёт SQLite. Если нужно обслуживать интернет-магазин или учебную систему, нужна клиент-серверная СУБД. Файл-серверная модель исторически важна, но для современных многопользовательских систем обычно проигрывает.

## 9. Тонкий и толстый клиент. Многоуровневые решения. Распределенная обработка   
### Конкретика для ответа   
**Толстый клиент** — клиентское приложение, в котором сосредоточена значительная часть бизнес-логики, обработки данных и интерфейса. Сервер в такой архитектуре часто используется в основном как хранилище данных. Пример: настольная программа, которая сама проверяет правила, формирует отчёты и напрямую обращается к БД.   
**Тонкий клиент** — клиент, который выполняет в основном функции интерфейса, а бизнес-логика и обработка данных находятся на сервере приложений или сервере БД. Пример: браузер, который отправляет HTTP-запросы веб-приложению, а само приложение уже обращается к PostgreSQL.   
Простая двухуровневая архитектура:   
```
flowchart LR
    Client[Клиентское приложение: интерфейс + часть логики] --> DB[Сервер БД]

```
Здесь клиент напрямую соединяется с БД. Это проще, но опаснее: приходится раздавать доступ к базе множеству рабочих мест, сложнее обновлять бизнес-логику и контролировать безопасность.   
Трёхуровневая архитектура:   
```
flowchart LR
    UI[Тонкий клиент / браузер] --> APP[Сервер приложений]
    APP --> DB[Сервер БД]

```
Здесь клиент отвечает за ввод и отображение, сервер приложений содержит бизнес-правила, а сервер БД отвечает за хранение, транзакции и запросы. Например, интернет-магазин: браузер показывает корзину, сервер приложения проверяет наличие товара и считает скидки, PostgreSQL хранит товары, заказы и платежи.   
**Многоуровневое решение** — архитектура, где система делится более чем на три логических слоя: клиентский интерфейс, API gateway, сервер приложений, сервис авторизации, сервис отчётов, СУБД, кэш, очередь сообщений. Такое деление повышает масштабируемость и сопровождаемость, но усложняет администрирование.   
**Распределённая обработка** означает, что разные части вычислений выполняются на разных узлах системы. Например, клиент формирует запрос, сервер приложений проверяет права, сервер БД выполняет SQL, кэш Redis хранит часто используемые результаты, очередь сообщений передаёт задачи на фоновую обработку.   
```
flowchart LR
    Browser[Браузер] --> API[API / сервер приложений]
    API --> Cache[(Кэш)]
    API --> DB[(База данных)]
    API --> MQ[Очередь сообщений]
    MQ --> Worker[Фоновый обработчик]

```
Сравнение:   
|                                Признак   <br> |                               Толстый клиент   <br> |                           Тонкий клиент   <br> |
|:----------------------------------------------|:----------------------------------------------------|:-----------------------------------------------|
|                             Где логика   <br> |                           на рабочей станции   <br> |                              на сервере   <br> |
|                             Обновление   <br> |                      надо обновлять клиентов   <br> |                      обновляется сервер   <br> |
|                   Требования к клиенту   <br> |                                         выше   <br> |                                    ниже   <br> |
|                           Безопасность   <br> |                       сложнее контролировать   <br> |                    проще централизовать   <br> |
|                                 Пример   <br> |                               настольная CRM   <br> |                          веб-приложение   <br> |

На экзамене полезно подчеркнуть: «тонкий» и «толстый» клиент не означают размер программы в мегабайтах. Это характеристика распределения ответственности между клиентом, сервером приложений и сервером БД.   
Тонкий клиент выполняет минимум логики: отображает интерфейс, принимает ввод и отправляет запросы на сервер. Пример — браузер, работающий с веб-приложением. Основная бизнес-логика находится на сервере, а данные — в СУБД. Плюсы тонкого клиента: централизованное обновление, контроль безопасности, меньшие требования к устройству. Минусы: зависимость от сети и сервера.   
Толстый клиент содержит значительную часть логики на стороне пользователя. Он может кэшировать данные, проверять правила, выполнять вычисления, иногда напрямую обращаться к БД. Пример — настольная бухгалтерская система. Плюсы: богатый интерфейс, часть работы offline, разгрузка сервера. Минусы: сложнее обновлять, выше риск рассинхронизации и утечки логики.   
```
graph TD
    Thin[Тонкий клиент: UI] --> App[Сервер приложения]
    App --> DB[(БД)]

graph TD
    Thick[Толстый клиент: UI + логика + кэш] --> DB[(Сервер БД)]

```
Многоуровневая архитектура разделяет систему на уровень представления, уровень бизнес-логики и уровень данных. Уровень представления отвечает за интерфейс. Уровень бизнес-логики применяет правила: оформление заказа, расчёт цены, проверку доступа. Уровень данных хранит информацию в СУБД, кэше, файловом хранилище или очереди.   
```
graph LR
    U[Пользователь] --> UI[Представление]
    UI --> BL[Бизнес-логика]
    BL --> DB[(СУБД)]
    BL --> Cache[(Кэш)]
    BL --> MQ[(Очередь)]

```
Распределённая обработка означает, что части задачи выполняются на разных узлах. Например, API Gateway принимает запрос, сервис каталога отвечает за товары, сервис заказов — за заказы, сервис оплаты — за платежи, а сервис уведомлений получает события из очереди. Это повышает масштабируемость и отказоустойчивость, но усложняет согласованность, мониторинг и транзакции.   
```
graph TD
    Client[Клиент] --> GW[API Gateway]
    GW --> Catalog[Сервис каталога]
    GW --> Orders[Сервис заказов]
    GW --> Pay[Сервис оплаты]
    Orders --> ODB[(БД заказов)]
    Catalog --> CDB[(БД каталога)]
    Orders --> MQ[Очередь]
    MQ --> Notify[Уведомления]

```
На экзамене важно не абсолютизировать понятия: современные веб-приложения часто занимают середину. Браузер может выполнять много JavaScript-логики, мобильное приложение может иметь локальную SQLite-БД и синхронизацию, но критические операции всё равно выполняются на сервере. Главное — объяснить распределение ответственности между клиентом, сервером приложений и уровнем данных.

## 10. Нормальные формы и процесс нормализации   
### Конкретика для ответа   
**Нормализация** — это процесс преобразования схемы реляционной БД с целью уменьшения избыточности данных и устранения аномалий вставки, обновления и удаления. Основа нормализации — анализ зависимостей между атрибутами.   
**Функциональная зависимость** `X → Y` означает: если две строки имеют одинаковое значение набора атрибутов `X`, то они обязаны иметь одинаковое значение набора атрибутов `Y`. Например, `student\_id → full\_name`, потому что идентификатор студента однозначно определяет его ФИО.   
Три главные аномалии:   
|             Аномалия   <br> |                                                                                                Суть   <br> |                                                                                                                 Пример   <br> |
|:----------------------------|:-----------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------|
|           Обновления   <br> |                                              одно и то же значение надо менять в нескольких строках   <br> |                                                                         название группы повторяется у каждого студента   <br> |
|              Вставки   <br> |                                                              нельзя добавить факт без другого факта   <br> |                                                                          нельзя добавить новую дисциплину без студента   <br> |
|             Удаления   <br> |                                                 удаление одной строки уничтожает другой важный факт   <br> |                                                        удалили последнего студента группы и потеряли сведения о группе   <br> |

**1НФ**: все значения атрибутов атомарны, нет повторяющихся групп и списков в одной ячейке. Нельзя хранить `phones = '111,222,333'`; надо вынести телефоны в отдельные строки.   
**2НФ**: отношение находится в 1НФ, и каждый неключевой атрибут полностью зависит от всего составного ключа, а не от его части. Нарушение возникает в таблице `enrollments(student\_id, discipline\_id, student\_name, discipline\_name, mark)`, где ключ `(student\_id, discipline\_id)`, но `student\_name` зависит только от `student\_id`.   
**3НФ**: отношение находится во 2НФ, и неключевые атрибуты не зависят транзитивно от ключа через другие неключевые атрибуты. Пример нарушения: `student\_id → group\_id`, `group\_id → curator\_name`, значит `student\_id → curator\_name` транзитивно.   
**НФБК (BCNF)**: для каждой нетривиальной функциональной зависимости `X → Y` левая часть `X` должна быть суперключом. BCNF строже 3НФ и устраняет случаи, когда детерминант не является ключом.   
**4НФ** устраняет нетривиальные многозначные зависимости. Пример: у преподавателя независимо несколько языков и несколько дисциплин. Хранить всё в одной таблице нельзя, иначе появится декартово произведение языков и дисциплин.   
**5НФ** устраняет зависимости соединения, когда отношение без потерь раскладывается на три и более проекции, и эти проекции лучше отражают независимые факты.   
Короткая формула ответа: нормализация переводит таблицы от «всё в одной большой таблице» к набору отношений, где каждый факт хранится один раз, зависит от ключа, всего ключа и ничего кроме ключа.   
Нормализация — процесс преобразования реляционной схемы для уменьшения избыточности и устранения аномалий вставки, обновления и удаления. Аномалия обновления возникает, когда одно и то же значение нужно менять во многих строках. Аномалия вставки — когда нельзя добавить факт без другого факта. Аномалия удаления — когда удаление одной строки случайно уничтожает важную информацию.   
Первая нормальная форма требует атомарности значений: в ячейке не должно быть списков. Поле `products = 'мышь, клавиатура'` нарушает 1НФ. Нужно вынести позиции заказа в отдельные строки или таблицу `order\_items`.   
Вторая нормальная форма требует 1НФ и отсутствия частичных зависимостей от части составного ключа. Если в `order\_items(order\_id, product\_id, product\_name, quantity)` ключ `(order\_id, product\_id)`, то `product\_name` зависит только от `product\_id`, значит его надо вынести в `products`.   
Третья нормальная форма требует отсутствия транзитивных зависимостей неключевых атрибутов от ключа. В `students(student\_id, group\_id, group\_name)` есть зависимость `student\_id → group\_id → group\_name`; значит `group\_name` нужно хранить в `groups`.   
НФБК усиливает 3НФ: для каждой нетривиальной функциональной зависимости `X → Y` детерминант `X` должен быть суперключом. Это устраняет сложные случаи с пересекающимися потенциальными ключами.   
4НФ работает с многозначными зависимостями. Если преподаватель имеет несколько телефонов и несколько дисциплин, их нельзя хранить в одной таблице с перемножением строк; нужны `teacher\_phones` и `teacher\_disciplines`. 5НФ работает с зависимостями соединения и применяется к сложным многоместным фактам.   
```
graph TD
    U[Ненормализованная таблица] --> NF1[1НФ: атомарность]
    NF1 --> NF2[2НФ: нет частичных зависимостей]
    NF2 --> NF3[3НФ: нет транзитивных зависимостей]
    NF3 --> BCNF[НФБК: каждый детерминант - суперключ]
    BCNF --> NF4[4НФ: многозначные зависимости]
    NF4 --> NF5[5НФ: зависимости соединения]

```
Нормализация не является самоцелью. Обычно для прикладных OLTP-систем хорошей целью является 3НФ или НФБК. Денормализация допустима ради производительности, но только осознанно: например, хранение агрегатов или копий названий должно контролироваться правилами обновления.

## 11. Процесс нормализации с первой нормальной формы до нормальной формы Бойса-Кодда   
### Конкретика для ответа   
Процесс нормализации удобно показать на одной исходной таблице. Пусть есть ненормализованная ведомость:   
| student\_id   <br> | student\_name   <br> | group\_name   <br> | disciplines   <br> |                     teachers   <br> | marks   <br> |
|:-------------------|:---------------------|:-------------------|:-------------------|:------------------------------------|:-------------|
|           1   <br> |        Иванов   <br> |        4311   <br> |     БД, SQL   <br> |              Петров, Сидоров   <br> |  5, 4   <br> |

Здесь нарушена **1НФ**, потому что в полях `disciplines`, `teachers`, `marks` хранятся списки, а не атомарные значения. Для перехода к 1НФ надо сделать так, чтобы каждая ячейка содержала одно значение:   
| student\_id   <br> | student\_name   <br> | group\_name   <br> | discipline   <br> |        teacher   <br> | mark   <br> |
|:-------------------|:---------------------|:-------------------|:------------------|:----------------------|:------------|
|           1   <br> |        Иванов   <br> |        4311   <br> |         БД   <br> |         Петров   <br> |    5   <br> |
|           1   <br> |        Иванов   <br> |        4311   <br> |        SQL   <br> |        Сидоров   <br> |    4   <br> |

Теперь таблица в 1НФ, но нарушает **2НФ**. Если ключ считать составным `(student\_id, discipline)`, то `student\_name` зависит только от `student\_id`, а не от всего ключа. `teacher` может зависеть от `discipline`, а не от пары целиком. Нужно разделить данные:   
```
students(student_id PK, student_name, group_id FK)
groups(group_id PK, group_name)
disciplines(discipline_id PK, discipline_name)
marks(student_id FK, discipline_id FK, mark,
      PRIMARY KEY(student_id, discipline_id))

```
После этого каждое отношение описывает один вид фактов: студент, группа, дисциплина, оценка.   
Для перехода к **3НФ** надо устранить транзитивные зависимости. Если в таблице `students` хранить `group\_name` и `curator\_name`, получится зависимость `student\_id → group\_id`, `group\_id → group\_name, curator\_name`. Значит, сведения о группе надо хранить отдельно:   
```
CREATE TABLE groups (
    group_id integer PRIMARY KEY,
    group_name text NOT NULL UNIQUE,
    curator_name text
);

CREATE TABLE students (
    student_id integer PRIMARY KEY,
    student_name text NOT NULL,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
Для перехода к **BCNF** проверяют каждую функциональную зависимость. Если есть зависимость `teacher → discipline`, но `teacher` не является ключом исходной таблицы `schedule(group\_id, discipline, teacher)`, то таблица может нарушать BCNF. Её можно разложить:   
```
teacher_disciplines(teacher, discipline)
group_teachers(group_id, teacher)

```
При нормализации важно требовать **соединения без потерь**: после разложения исходные данные должны восстанавливаться соединением таблиц. Также желательно сохранять зависимости, чтобы ограничения можно было проверять без сложных соединений. Поэтому нормализация — не механическое дробление таблиц, а управляемое преобразование схемы по зависимостям.   
Рассмотрим таблицу результатов экзаменов: `exam(student\_id, student\_name, group\_id, group\_name, discipline\_id, discipline\_name, teacher\_id, teacher\_name, grade)`. Если все значения атомарны, таблица находится в 1НФ. Но в ней много избыточности: имя студента повторяется во всех его оценках, название группы повторяется у всех студентов, название дисциплины и имя преподавателя повторяются для каждой сдачи.   
Если ключ результата — `(student\_id, discipline\_id)`, то `grade` зависит от всего ключа. Но `student\_name` и `group\_id` зависят только от `student\_id`; `discipline\_name` и `teacher\_id` зависят только от `discipline\_id`. Это частичные зависимости, нарушающие 2НФ. Для перехода ко 2НФ данные разделяют на `students`, `disciplines`, `exam\_results`.   
После этого остаются транзитивные зависимости. В `students`: `student\_id → group\_id`, а `group\_id → group\_name`, значит `group\_name` транзитивно зависит от студента. В `disciplines`: `discipline\_id → teacher\_id`, а `teacher\_id → teacher\_name`. Для перехода к 3НФ создают отдельные таблицы `groups` и `teachers`.   
```
erDiagram
    GROUPS ||--o{ STUDENTS : contains
    TEACHERS ||--o{ DISCIPLINES : teaches
    STUDENTS ||--o{ EXAM_RESULTS : receives
    DISCIPLINES ||--o{ EXAM_RESULTS : has
    GROUPS { int group_id PK string group_name }
    STUDENTS { int student_id PK string name int group_id FK }
    TEACHERS { int teacher_id PK string name }
    DISCIPLINES { int discipline_id PK string name int teacher_id FK }
    EXAM_RESULTS { int student_id PK,FK int discipline_id PK,FK int grade }

```
НФБК требует проверить все функциональные зависимости. Для каждой зависимости `X → Y` множество `X` должно быть суперключом. Пример нарушения: `consultations(student\_id, discipline, teacher)`, где `(student\_id, discipline) → teacher` и `teacher → discipline`, потому что каждый преподаватель ведёт одну дисциплину. Детерминант `teacher` не является суперключом всей таблицы, значит НФБК нарушена. Разложение: `teacher\_disciplines(teacher, discipline)` и `student\_teachers(student\_id, teacher)`.   
Главная логика нормализации: 1НФ убирает списки в ячейках, 2НФ убирает зависимости от части составного ключа, 3НФ убирает транзитивные зависимости, НФБК требует, чтобы любой детерминант был ключом. При разложении важно сохранять соединение без потерь, иначе схема будет формально красивой, но данные не восстановятся корректно.

## 12. Четвертая и пятая нормальные формы. Примеры нормализации   
### Конкретика для ответа   
**Четвёртая нормальная форма (4НФ)** связана не с функциональными, а с многозначными зависимостями. **Многозначная зависимость** `X ↠ Y` означает: одному значению `X` соответствует множество значений `Y`, причём это множество независимо от других атрибутов отношения. Отношение находится в 4НФ, если для каждой нетривиальной многозначной зависимости `X ↠ Y` левая часть `X` является суперключом.   
Классический пример нарушения 4НФ:   
|      teacher   <br> |             language   <br> |            discipline   <br> |
|:--------------------|:----------------------------|:-----------------------------|
|       Иванов   <br> |           Английский   <br> |           Базы данных   <br> |
|       Иванов   <br> |           Английский   <br> |                   SQL   <br> |
|       Иванов   <br> |             Немецкий   <br> |           Базы данных   <br> |
|       Иванов   <br> |             Немецкий   <br> |                   SQL   <br> |

Смысл: преподаватель Иванов знает два языка и ведёт две дисциплины. Но знание языка не связано с дисциплиной. Таблица создаёт искусственное декартово произведение. Если добавить третий язык, придётся дублировать его для всех дисциплин. Здесь есть независимые многозначные зависимости: `teacher ↠ language` и `teacher ↠ discipline`.   
Правильное разложение для 4НФ:   
```
teacher_languages(teacher, language)
teacher_disciplines(teacher, discipline)

```
**Пятая нормальная форма (5НФ)** связана с зависимостями соединения. Отношение находится в 5НФ, если каждая нетривиальная зависимость соединения следует из потенциальных ключей. Проще: таблицу нельзя без потерь разложить на несколько меньших таблиц так, чтобы это разложение отражало независимые факты лучше исходной таблицы.   
Пример для 5НФ: поставщик `S`, деталь `P`, проект `J`.   
| supplier   <br> | part   <br> | project   <br> |
|:----------------|:------------|:---------------|
|       S1   <br> |   P1   <br> |      J1   <br> |
|       S1   <br> |   P2   <br> |      J1   <br> |
|       S1   <br> |   P1   <br> |      J2   <br> |

Иногда факт «поставщик поставляет деталь проекту» определяется тремя независимыми бинарными фактами: поставщик работает с деталью, поставщик работает с проектом, деталь используется в проекте. Тогда отношение можно разложить:   
```
SP(supplier, part)
SJ(supplier, project)
PJ(part, project)

```
Но это разложение допустимо только если соединение этих трёх таблиц не создаёт ложных троек. Поэтому 5НФ применяется осторожно и встречается реже, чем 1НФ–3НФ и BCNF.   
Краткое различие:   
|      Норма   <br> |                                              Что устраняет   <br> |                                 Тип зависимости   <br> |                                               Пример проблемы   <br> |
|:------------------|:------------------------------------------------------------------|:-------------------------------------------------------|:---------------------------------------------------------------------|
|        4НФ   <br> |                             независимые множества значений   <br> |                        многозначная зависимость   <br> |                              языки преподавателя × дисциплины   <br> |
|        5НФ   <br> |                             сложные зависимости соединения   <br> |                          зависимость соединения   <br> |                                       поставщик–деталь–проект   <br> |

Экзаменационный вывод: 4НФ нужна, когда одна сущность имеет несколько независимых наборов характеристик, а 5НФ нужна, когда многоместная связь корректно распадается на несколько меньших связей без потери смысла и без появления ложных комбинаций.   
Четвёртая нормальная форма связана с многозначными зависимостями. Многозначная зависимость `A ↠ B` означает, что одному значению `A` соответствует множество значений `B`, независимое от других атрибутов. Проблема возникает, когда в одной таблице хранятся два независимых множества. Например, преподаватель имеет несколько телефонов и ведёт несколько дисциплин.   
Ошибочная таблица:   
|        teacher   <br> | phone   <br> |            discipline   <br> |
|:----------------------|:-------------|:-----------------------------|
|        Сидоров   <br> |   111   <br> |           Базы данных   <br> |
|        Сидоров   <br> |   111   <br> |                   SQL   <br> |
|        Сидоров   <br> |   222   <br> |           Базы данных   <br> |
|        Сидоров   <br> |   222   <br> |                   SQL   <br> |

Здесь телефоны и дисциплины перемножаются. Чтобы добавить третий телефон, придётся добавить строки для всех дисциплин. Для 4НФ отношение разбивают:   
|        teacher   <br> | phone   <br> |
|:----------------------|:-------------|
|        Сидоров   <br> |   111   <br> |
|        Сидоров   <br> |   222   <br> |

|        teacher   <br> |            discipline   <br> |
|:----------------------|:-----------------------------|
|        Сидоров   <br> |           Базы данных   <br> |
|        Сидоров   <br> |                   SQL   <br> |

```
graph TD
    Bad[teacher, phone, discipline] --> P[teacher_phones]
    Bad --> D[teacher_disciplines]

```
Пятая нормальная форма связана с зависимостями соединения. Она требует, чтобы отношение нельзя было без потерь разложить на более мелкие отношения иначе как по зависимостям, вытекающим из ключей. Классический пример — поставщики, детали и проекты: `SPJ(supplier, part, project)`. Иногда тройной факт можно восстановить из бинарных отношений `SP`, `SJ`, `PJ`. Но это допустимо только если бизнес-правила действительно говорят, что такие независимые связи порождают допустимую тройку.   
5НФ применяется реже, потому что требует глубокого анализа предметной области. Если разложить отношение неправильно, соединение проекций создаст ложные строки. Поэтому 4НФ обычно распознаётся по независимым спискам, а 5НФ — по сложным многоместным фактам, восстанавливаемым соединением. На экзамене нужно подчеркнуть: 4НФ устраняет избыточность от многозначных зависимостей, 5НФ — от нетривиальных зависимостей соединения.

## 13. Проектирование БД: инфологическое, даталогическое, физическое   
### Конкретика для ответа   
Проектирование БД обычно делят на три уровня: **инфологическое**, **даталогическое** и **физическое**. Эти этапы соответствуют движению от предметной области к конкретной СУБД.   
**Инфологическое проектирование** — построение модели предметной области, независимой от конкретной СУБД. На этом этапе выясняют, какие объекты существуют, какими свойствами обладают и как связаны между собой. Результатом является концептуальная ER-модель. Например, для учебной БД выделяются сущности `Студент`, `Группа`, `Дисциплина`, `Преподаватель`, `Оценка`; задаются связи: студент принадлежит группе, студент получает оценки, дисциплина читается преподавателем.   
**Даталогическое проектирование** — преобразование инфологической модели в логическую схему выбранной модели данных, обычно реляционной. На этом этапе сущности превращаются в таблицы, атрибуты — в столбцы, связи — во внешние ключи или промежуточные таблицы. Здесь выбираются первичные ключи, внешние ключи, нормальные формы и ограничения.   
Пример перехода:   
```
Инфологическая сущность: Студент
Атрибуты: ФИО, дата рождения, группа

Даталогическая таблица:
students(student_id PK, full_name, birth_date, group_id FK)

```
**Физическое проектирование** — настройка схемы под конкретную СУБД и условия эксплуатации. Здесь выбирают типы данных, индексы, партиционирование, tablespace, параметры хранения, резервное копирование, права доступа, стратегию выполнения запросов. Например, для таблицы `marks` можно создать индекс по `(student\_id, discipline\_id)`, потому что часто ищут оценки конкретного студента.   
```
CREATE INDEX idx_marks_student_discipline
ON marks(student_id, discipline_id);

```
Схема этапов:   
```
flowchart TD
    A[Анализ предметной области] --> B[Инфологическая модель: сущности, связи, атрибуты]
    B --> C[Даталогическая модель: таблицы, ключи, нормализация]
    C --> D[Физическая модель: типы, индексы, хранение, права]
    D --> E[Реализация в СУБД]

```
Сравнительная таблица:   
|                         Этап   <br> |                                           Главный вопрос   <br> |                                   Результат   <br> |                                Пример решения   <br> |
|:------------------------------------|:----------------------------------------------------------------|:---------------------------------------------------|:-----------------------------------------------------|
|               Инфологический   <br> |                           что есть в предметной области?   <br> |                                   ER-модель   <br> |                      студент связан с группой   <br> |
|               Даталогический   <br> |                           как это представить логически?   <br> |                                схема таблиц   <br> |                      `students`, `groups`, FK   <br> |
|                   Физический   <br> |                              как это эффективно хранить?   <br> |                 SQL DDL, индексы, настройки   <br> |                  B-tree индекс, тип `integer`   <br> |

Экзаменационный вывод: инфологическое проектирование описывает смысл данных, даталогическое — их логическую структуру в выбранной модели, физическое — способ реализации в конкретной СУБД. Ошибка на раннем этапе обычно дороже, чем ошибка физической настройки, потому что неправильные сущности и связи потом трудно исправить.   
Проектирование БД переводит описание предметной области в работающую структуру хранения. Обычно выделяют инфологическое, даталогическое и физическое проектирование. Эти этапы идут от смысла к логической модели и затем к реализации в конкретной СУБД.   
Инфологическое проектирование не зависит от конкретной СУБД. На этом этапе выявляют сущности, атрибуты, связи и бизнес-правила. Например, для учебной системы: студент, группа, дисциплина, преподаватель, оценка. Определяется, что группа содержит студентов, преподаватель ведёт дисциплины, студент получает оценки. Результат — ER-модель или описание предметной области.   
Даталогическое проектирование переводит инфологическую модель в логическую схему выбранной модели данных. Для реляционной БД сущности становятся таблицами, атрибуты — столбцами, связи 1:N — внешними ключами, связи M:N — промежуточными таблицами. На этом этапе определяются ключи, домены, нормальные формы и ограничения.   
Физическое проектирование адаптирует логическую схему к конкретной СУБД и нагрузке. Выбираются типы данных, индексы, партиционирование, схемы, права, параметры хранения, резервное копирование. Например, в PostgreSQL можно создать индекс по `group\_id`, если часто выбираются студенты группы.   
```
graph TD
    I[Инфологическое: сущности и связи] --> D[Даталогическое: таблицы и ключи]
    D --> P[Физическое: индексы, типы, хранение]

```
```
CREATE TABLE exam_results (
    student_id integer REFERENCES students(student_id),
    discipline_id integer REFERENCES disciplines(discipline_id),
    grade integer CHECK (grade BETWEEN 2 AND 5),
    PRIMARY KEY (student_id, discipline_id)
);
CREATE INDEX idx_exam_discipline ON exam_results(discipline_id);

```
Если пропустить инфологический этап, можно быстро написать таблицы, но неверно понять предметную область. Если пропустить даталогический этап, ER-диаграмма будет плохо отображена в SQL. Если пропустить физический этап, логически правильная база может работать медленно. Хороший проект итерационен: новые требования могут возвращать проектировщика к более ранним этапам.

## 14. Проектирование в нотации П. Чена. Типы связей. Атрибуты. Пример   
### Конкретика для ответа   
Нотация Питера Чена — классическая ER-нотация для инфологического проектирования БД. В ней предметная область описывается через **сущности**, **атрибуты** и **связи**.   
**Сущность** — множество однотипных объектов предметной области. В нотации Чена сущность изображается прямоугольником. Примеры: `Студент`, `Группа`, `Дисциплина`, `Преподаватель`.   
**Атрибут** — свойство сущности или связи. В классической нотации Чена атрибут изображается овалом. Примеры атрибутов студента: `student\_id`, `ФИО`, `дата\_рождения`. Ключевой атрибут подчёркивается. Составной атрибут может раскладываться на части: `ФИО` на `фамилия`, `имя`, `отчество`. Многозначный атрибут изображается двойным овалом, например несколько телефонов студента.   
**Связь** — ассоциация между сущностями. В нотации Чена связь изображается ромбом. Примеры: студент «принадлежит» группе, преподаватель «читает» дисциплину, студент «сдаёт» дисциплину.   
Типы связей:   
|                            Тип   <br> |            Обозначение   <br> |                                    Пример   <br> |
|:--------------------------------------|:------------------------------|:-------------------------------------------------|
|                  один-к-одному   <br> |                    1:1   <br> |                         человек — паспорт   <br> |
|                 один-ко-многим   <br> |                    1:N   <br> |                         группа — студенты   <br> |
|               многие-ко-многим   <br> |                    M:N   <br> |                     студенты — дисциплины   <br> |

Пример проектирования учебной части:   
```
erDiagram
    GROUP ||--o{ STUDENT : contains
    STUDENT }o--o{ DISCIPLINE : studies
    TEACHER ||--o{ DISCIPLINE : teaches
    STUDENT { int student_id PK string full_name date birth_date }
    GROUP { int group_id PK string group_name }
    DISCIPLINE { int discipline_id PK string name int hours }
    TEACHER { int teacher_id PK string full_name }

```
В терминах Чена этот пример читается так: сущность `Группа` связана со `Студентом` отношением 1:N, потому что одна группа содержит много студентов, а студент принадлежит одной группе. Сущность `Студент` связана с `Дисциплиной` отношением M:N, потому что один студент изучает много дисциплин, а одна дисциплина изучается многими студентами. При переходе к реляционной схеме связь M:N превращается в отдельную таблицу:   
```
CREATE TABLE student_disciplines (
    student_id integer REFERENCES students(student_id),
    discipline_id integer REFERENCES disciplines(discipline_id),
    semester integer NOT NULL,
    PRIMARY KEY (student_id, discipline_id)
);

```
Если связь имеет собственные атрибуты, они относятся не к одной сущности, а к факту связи. Например, `mark` и `exam\_date` логично хранить в связи «студент сдаёт дисциплину», а не в таблице студента и не в таблице дисциплины.   
Экзаменационный вывод: нотация Чена нужна для концептуального описания предметной области до выбора конкретной СУБД. Она помогает увидеть сущности, их атрибуты, типы связей и затем корректно перейти к реляционным таблицам.   
Нотация Питера Чена — классическая ER-нотация для инфологического проектирования. Сущности изображаются прямоугольниками, связи — ромбами, атрибуты — овалами. Её смысл — отделить объект предметной области, его свойства и факт связи с другими объектами.   
Сущность — класс объектов: студент, группа, дисциплина, преподаватель. Экземпляр сущности — конкретный студент Иванов или дисциплина «Базы данных». Сильная сущность имеет собственный ключ. Слабая сущность зависит от другой, например позиция заказа зависит от заказа.   
Атрибут — характеристика сущности или связи. Атрибуты бывают простыми, составными, однозначными, многозначными, производными и ключевыми. Например, ФИО можно считать составным атрибутом, телефон — многозначным, возраст — производным от даты рождения.   
Связи бывают 1:1, 1:N, M:N. Связь 1:1: человек и паспорт в упрощённой модели. Связь 1:N: группа содержит много студентов, студент относится к одной группе. Связь M:N: студенты изучают дисциплины, дисциплины изучаются многими студентами. Связь может иметь собственные атрибуты: оценка относится к факту сдачи дисциплины студентом.   
```
graph TD
    Student[СТУДЕНТ] --- SId((student_id))
    Student --- SName((ФИО))
    Group[ГРУППА] --- GId((group_id))
    Group --- GName((название))
    Discipline[ДИСЦИПЛИНА] --- DId((discipline_id))
    Teacher[ПРЕПОДАВАТЕЛЬ] --- TId((teacher_id))
    Belongs{ПРИНАДЛЕЖИТ} --- Student
    Belongs --- Group
    Studies{ИЗУЧАЕТ} --- Student
    Studies --- Discipline
    Studies --- Grade((оценка))
    Teaches{ВЕДЁТ} --- Teacher
    Teaches --- Discipline

```
Переход к реляционной схеме: сильные сущности становятся таблицами, атрибуты — столбцами, ключевые атрибуты — первичными ключами. Связь 1:N реализуется внешним ключом на стороне N. Связь M:N превращается в отдельную таблицу, содержащую внешние ключи и атрибуты связи.   
```
CREATE TABLE student_disciplines (
    student_id integer REFERENCES students(student_id),
    discipline_id integer REFERENCES disciplines(discipline_id),
    grade integer CHECK (grade BETWEEN 2 AND 5),
    PRIMARY KEY (student_id, discipline_id)
);

```
Нотация Чена полезна тем, что заставляет правильно определить, что является сущностью, что атрибутом, а что связью. Например, оценка — не свойство только студента и не свойство только дисциплины, а атрибут связи между студентом и дисциплиной.

## 15. Индексирование: B-дерево, битовые карты   
### Конкретика для ответа   
**Индекс** в БД — это дополнительная структура данных, ускоряющая поиск строк по значениям одного или нескольких столбцов. Индекс похож на предметный указатель в книге: вместо просмотра всей таблицы СУБД быстро находит место, где находятся нужные строки. Индекс ускоряет чтение, но замедляет вставку, удаление и обновление, потому что его тоже надо поддерживать.   
**B-дерево** — сбалансированная древовидная структура, в которой данные отсортированы по ключу, а путь от корня до любого листа имеет примерно одинаковую длину. В СУБД часто используется разновидность B+tree: внутренние узлы направляют поиск, а листья содержат ссылки на строки или сами значения индекса.   
```
flowchart TD
    R[Корень: 40] --> L[Лист: 1..39]
    R --> M[Лист: 40..79]
    R --> H[Лист: 80..120]

```
B-tree эффективен для операций:   
```
WHERE student_id = 10
WHERE birth_date BETWEEN DATE '2000-01-01' AND DATE '2002-12-31'
ORDER BY full_name

```
Пример создания индекса:   
```
CREATE INDEX idx_students_group_id
ON students(group_id);

```
Если часто выполняется запрос `SELECT \* FROM students WHERE group\_id = 101`, индекс по `group\_id` может существенно ускорить поиск.   
**Битовая карта (bitmap index)** — индекс, в котором для каждого значения атрибута хранится битовый вектор: 1 означает, что строка имеет это значение, 0 — что не имеет. Такой индекс особенно эффективен для столбцов с малым числом различных значений: пол, статус, категория, флаг активности.   
Пример для атрибута `status`:   
| row\_id   <br> |   status   <br> |
|:---------------|:----------------|
|       1   <br> |   active   <br> |
|       2   <br> | archived   <br> |
|       3   <br> |   active   <br> |
|       4   <br> |  blocked   <br> |

Битовые векторы:   
|         Значение   <br> |             Битовая карта   <br> |
|:------------------------|:---------------------------------|
|           active   <br> |                      1010   <br> |
|         archived   <br> |                      0100   <br> |
|          blocked   <br> |                      0001   <br> |

Преимущество bitmap-индексов — быстрые логические операции `AND`, `OR`, `NOT`. Например, условие `status = 'active' AND gender = 'F'` можно вычислить как побитовое `AND` двух карт. Недостаток — плохая пригодность для часто изменяемых столбцов с высокой кардинальностью, например `email` или `passport\_number`.   
Сравнение:   
|                           Признак   <br> |                                                                    B-tree   <br> |                                  Bitmap   <br> |
|:-----------------------------------------|:---------------------------------------------------------------------------------|:-----------------------------------------------|
|                         Лучше для   <br> |                                    высокоселективных значений, диапазонов   <br> |                    малой кардинальности   <br> |
|                     Примеры полей   <br> |                                                     `id`, `date`, `email`   <br> |        `status`, `gender`, `is\_active`   <br> |
|                        Обновления   <br> |                                                          обычно приемлемы   <br> |                     могут быть дорогими   <br> |
|                 Диапазонный поиск   <br> |                                                                     хорош   <br> |                      не основная задача   <br> |

Экзаменационный вывод: B-tree является универсальным индексом для равенства, диапазонов и сортировки, а bitmap-индекс полезен для аналитических запросов по признакам с небольшим числом значений.   
Индекс — вспомогательная структура, ускоряющая поиск строк. Без индекса СУБД часто просматривает таблицу последовательно. Индекс работает как предметный указатель в книге: он занимает место и требует обновления при изменениях, но ускоряет чтение.   
B-tree — самый распространённый универсальный индекс. Он хранит ключи в отсортированном сбалансированном дереве. Подходит для равенства, диапазонов, сортировки: `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, `LIKE 'abc%'`. В PostgreSQL B-tree создаётся по умолчанию командой `CREATE INDEX`.   
```
graph TD
    R[50] --> A[10|30]
    R --> B[70|90]
    A --> A1[1,5,9]
    A --> A2[12,20,29]
    B --> B1[51,60]
    B --> B2[91,99]

```
```
CREATE INDEX idx_students_last_name ON students(last_name);

```
Битовые карты представляют множество строк через биты. Для каждого значения признака создаётся битовая последовательность: 1 означает, что строка имеет значение, 0 — не имеет. Они особенно полезны для признаков низкой кардинальности: статус, пол, категория, регион.   
| row   <br> |    status   <br> |
|:-----------|:-----------------|
|   1   <br> |      paid   <br> |
|   2   <br> |       new   <br> |
|   3   <br> |      paid   <br> |
|   4   <br> | cancelled   <br> |
|   5   <br> |       new   <br> |

|    status   <br> | bitmap   <br> |
|:-----------------|:--------------|
|      paid   <br> |  10100   <br> |
|       new   <br> |  01001   <br> |

Для условия `status='paid' OR status='new'` можно выполнить битовое OR: `10100 OR 01001 = 11101`. Битовые индексы хороши для аналитики, но хуже для часто обновляемых OLTP-таблиц. Также важно различать постоянный bitmap index и bitmap scan, когда СУБД строит битовую карту во время выполнения запроса по обычным индексам.   
|                     Критерий   <br> |                                                       B-tree   <br> |                                                       Bitmap   <br> |
|:------------------------------------|:--------------------------------------------------------------------|:--------------------------------------------------------------------|
|                    Лучше для   <br> |                             равенство, диапазоны, сортировка   <br> |                             фильтры по малому числу значений   <br> |
|               Кардинальность   <br> |                                            средняя и высокая   <br> |                                                       низкая   <br> |
|                   Обновления   <br> |                                             переносит хорошо   <br> |                                           может быть дорогим   <br> |
|                       Пример   <br> |                                              email, id, date   <br> |                                             status, category   <br> |

Индексирование — компромисс: чтение быстрее, запись медленнее, база больше. Индексы выбирают по реальным запросам, а не по желанию украсить каждый столбец.

## 16. Индексирование: первичный, кластерный и некластерный индексы   
### Конкретика для ответа   
**Первичный индекс** обычно связан с первичным ключом таблицы. Когда объявляется `PRIMARY KEY`, СУБД создаёт механизм уникального поиска по ключу. В PostgreSQL первичный ключ автоматически создаёт уникальный B-tree индекс. Важно различать логическое ограничение `PRIMARY KEY` и физическую структуру индекса: первичный ключ гарантирует уникальность и отсутствие `NULL`, а индекс является средством эффективной проверки и поиска.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL
);

```
**Кластерный индекс** — индекс, порядок которого определяет физический или близкий к физическому порядок хранения строк таблицы. Идея: строки на диске расположены примерно в том же порядке, что и ключ индекса. Это полезно для диапазонных запросов. Например, если таблица заказов физически упорядочена по `order\_date`, запросы за период читают меньше разрозненных страниц.   
Пример концепции:   
```
Кластеризация по order_date:
[2026-01-01][2026-01-02][2026-01-03] ...

```
В разных СУБД термин отличается. В SQL Server clustered index действительно задаёт физический порядок таблицы. В PostgreSQL команда `CLUSTER` физически переупорядочивает таблицу по индексу, но этот порядок не поддерживается автоматически после всех изменений.   
**Некластерный индекс** — отдельная структура, которая хранит ключи индекса и ссылки на строки таблицы, но не определяет физический порядок самих строк. У таблицы может быть несколько некластерных индексов: по email, по дате рождения, по группе.   
```
CREATE INDEX idx_students_email ON students(email);
CREATE INDEX idx_students_group ON students(group_id);

```
Пример различия:   
|              Вид индекса   <br> |                                                                               Что делает   <br> |                                          Сколько может быть   <br> |               Пример   <br> |
|:--------------------------------|:------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------|:----------------------------|
|                Первичный   <br> |                                         обеспечивает быстрый доступ по PK и уникальность   <br> |                                              обычно один PK   <br> |        `student\_id`   <br> |
|               Кластерный   <br> |                                              задаёт порядок хранения/кластеризации строк   <br> |                             обычно один фактический порядок   <br> |        `order\_date`   <br> |
|             Некластерный   <br> |                                                            отдельный указатель на строки   <br> |                                                       много   <br> | `email`, `group\_id`   <br> |

Проверочный пример: таблица `orders` содержит 10 млн строк. Если часто ищут заказ по `order\_id`, нужен первичный индекс. Если часто строят отчёты по периоду, полезна кластеризация или индекс по `order\_date`. Если часто ищут заказы пользователя, нужен некластерный индекс по `customer\_id`.   
Экзаменационный вывод: первичный индекс связан с идентификацией строк, кластерный — с порядком размещения данных, некластерный — с дополнительными путями доступа. Индекс нельзя считать бесплатным: он ускоряет чтение, но требует места и увеличивает стоимость изменений.   
Первичный индекс связан с первичным ключом. Первичный ключ уникально идентифицирует строку и не допускает `NULL`. Во многих СУБД при объявлении `PRIMARY KEY` автоматически создаётся уникальный индекс, чтобы быстро искать строки и проверять уникальность.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL
);

```
Кластерный индекс определяет или приближает физический порядок хранения строк. Если данные упорядочены по дате, диапазонные запросы по дате читают меньше разрозненных страниц. В некоторых СУБД таблица может иметь только один кластерный индекс, потому что физический порядок один. В PostgreSQL команда `CLUSTER` может переупорядочить таблицу по индексу, но порядок не поддерживается автоматически навсегда.   
Некластерный индекс хранится отдельно от таблицы и содержит ключи плюс ссылки на строки. Таблица может иметь много некластерных индексов: по email, внешнему ключу, дате, статусу. Они ускоряют поиск, но требуют обслуживания при `INSERT`, `UPDATE`, `DELETE`.   
```
graph TD
    T[(Таблица)]
    PK[Первичный индекс по id] --> T
    N1[Некластерный индекс по email] --> T
    N2[Некластерный индекс по group_id] --> T
    C[Кластеризация по дате] -. влияет на порядок .-> T

```
```
CREATE INDEX idx_students_email ON students(email);
CREATE INDEX idx_students_group ON students(group_id);

```
Первичный ключ — логическое ограничение, индекс — физическая структура доступа. Уникальный индекс может поддерживать альтернативную уникальность, например email. Кластерный индекс важен для диапазонных чтений. Некластерные индексы гибки, но избыточное количество индексов замедляет записи и увеличивает размер базы. Поэтому индексы проектируют по профилю запросов.

## 17. Понятие и свойства транзакций, изоляции. Примеры   
### Конкретика для ответа   
**Транзакция** — это логически неделимая последовательность операций с БД, переводящая базу из одного согласованного состояния в другое. Транзакция либо выполняется полностью, либо полностью отменяется. Пример: перевод 100 рублей со счёта A на счёт B состоит минимум из двух операций: списания и зачисления. Если списание произошло, а зачисление нет, база становится противоречивой.   
ACID-свойства:   
|                                    Свойство   <br> |                                                                                                                      Определение   <br> |                                                                             Пример   <br> |
|:---------------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------|
|                      Atomicity, атомарность   <br> |                                                             все операции транзакции выполняются целиком или не выполняются вовсе   <br> |                                          перевод не может быть наполовину выполнен   <br> |
|                Consistency, согласованность   <br> |                                                                                     транзакция сохраняет ограничения целостности   <br> |                                        баланс не уходит ниже разрешённого минимума   <br> |
|                  Isolation, изолированность   <br> |                                                               параллельные транзакции не должны некорректно влиять друг на друга   <br> |                                       два кассира не списывают один остаток дважды   <br> |
|                   Durability, долговечность   <br> |                                                                                    после `COMMIT` результат сохраняется при сбое   <br> |                                                 подтверждённый платёж не пропадает   <br> |

SQL-пример:   
```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;

```
Если возникла ошибка:   
```
ROLLBACK;

```
**Изоляция транзакций** определяет, какие изменения одной транзакции видны другим параллельным транзакциям. Основные проблемы изоляции:   
1. **Dirty read, грязное чтение** — транзакция читает данные, которые другая транзакция ещё не зафиксировала.   
2. **Non-repeatable read, неповторяемое чтение** — повторное чтение той же строки в одной транзакции даёт другой результат из-за фиксации чужого изменения.   
3. **Phantom read, фантомное чтение** — повторный запрос по условию возвращает новый набор строк, потому что другая транзакция вставила или удалила подходящие строки.   
   
Уровни изоляции SQL:   
|          Уровень   <br> |                                                                                                                    Смысл   <br> |
|:------------------------|:--------------------------------------------------------------------------------------------------------------------------------|
| Read Uncommitted   <br> |                                                               допускает чтение незафиксированных данных в некоторых СУБД   <br> |
|   Read Committed   <br> |                                                                                      видны только зафиксированные данные   <br> |
|  Repeatable Read   <br> |                                                                         повторное чтение уже прочитанных строк стабильно   <br> |
|     Serializable   <br> |                                                           результат эквивалентен последовательному выполнению транзакций   <br> |

Пример конфликта: два пользователя одновременно покупают последний билет. Без транзакций оба могут увидеть `available = 1` и оба оформить покупку. Правильное решение — выполнять проверку и изменение в одной транзакции с подходящими блокировками или уровнем изоляции.   
```
BEGIN;
SELECT available FROM tickets WHERE ticket_id = 10 FOR UPDATE;
UPDATE tickets SET available = available - 1 WHERE ticket_id = 10 AND available > 0;
COMMIT;

```
Экзаменационный вывод: транзакции нужны для надёжного выполнения связанных операций, а изоляция — для корректной параллельной работы пользователей.   
Транзакция — логическая единица работы с БД, состоящая из одной или нескольких операций. Она завершается `COMMIT` или отменяется `ROLLBACK`. Транзакции нужны, когда несколько операций образуют один смысловой факт: перевод денег, оформление заказа, запись результата экзамена.   
Свойства ACID: атомарность, согласованность, изолированность, долговечность. Атомарность означает «всё или ничего». Согласованность — переход из одного корректного состояния в другое. Изолированность — защита параллельных транзакций от неконтролируемого влияния. Долговечность — сохранение зафиксированных изменений после сбоя.   
```
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE account_id = 2;
COMMIT;

```
Если вторая операция не выполнится, нужен `ROLLBACK`, иначе деньги исчезнут из одного счёта и не появятся на другом.   
Аномалии изоляции: грязное чтение — чтение незакоммиченных данных; неповторяющееся чтение — повторное чтение строки даёт другое значение; фантомное чтение — повторный запрос по условию видит новые строки; потерянное обновление — результат одной транзакции перезаписывается другой.   
SQL-стандарт выделяет уровни изоляции: `READ UNCOMMITTED`, `READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`. Чем выше уровень, тем меньше аномалий, но выше стоимость конкурентного выполнения. PostgreSQL по умолчанию обычно использует `READ COMMITTED`, а `SERIALIZABLE` стремится обеспечить результат, эквивалентный последовательному выполнению транзакций.   
Пример потери обновления: два пользователя читают остаток товара 10. Первый продаёт 2 и пишет 8, второй продаёт 3 и пишет 7. Правильный остаток 5, но одно обновление потерялось. Безопаснее выполнять атомарное обновление:   
```
BEGIN;
UPDATE products
SET stock = stock - 3
WHERE product_id = 10 AND stock >= 3;
COMMIT;

```
```
sequenceDiagram
    participant T1 as Транзакция 1
    participant DB as БД
    participant T2 as Транзакция 2
    T1->>DB: BEGIN, UPDATE
    T2->>DB: SELECT/UPDATE
    DB-->>T2: видимость зависит от уровня изоляции
    T1->>DB: COMMIT

```
Транзакции также поддерживают `SAVEPOINT`, позволяя откатывать часть большой операции. На экзамене важно показать: транзакция сохраняет смысл операции, ACID описывает требования корректности, уровни изоляции регулируют параллельную видимость изменений.

## 18. Основные категории команд языка SQL. Примеры   
### Конкретика для ответа   
SQL-команды принято делить на категории по назначению. Это важно, потому что SQL — не только язык выборки, но и язык определения структуры, изменения данных, управления правами и транзакциями.   
**DDL (Data Definition Language)** — язык определения данных. Команды DDL создают, изменяют и удаляют объекты БД: таблицы, схемы, индексы, представления.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    group_id integer
);

ALTER TABLE students ADD COLUMN email text;
DROP TABLE old_students;

```
**DML (Data Manipulation Language)** — язык манипулирования данными. Команды DML изменяют содержимое таблиц.   
```
INSERT INTO students(student_id, full_name, group_id)
VALUES (1, 'Иванов Иван', 101);

UPDATE students SET group_id = 102 WHERE student_id = 1;
DELETE FROM students WHERE student_id = 1;

```
**DQL (Data Query Language)** — язык запросов к данным. Часто его рассматривают как часть DML, но на экзамене удобно выделить `SELECT` отдельно.   
```
SELECT s.full_name, g.group_name
FROM students s
JOIN groups g ON g.group_id = s.group_id
WHERE g.group_name = '4311';

```
**DCL (Data Control Language)** — язык управления доступом. Он назначает и отзывает права.   
```
GRANT SELECT ON students TO analyst;
REVOKE DELETE ON students FROM analyst;

```
**TCL (Transaction Control Language)** — язык управления транзакциями.   
```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
COMMIT;
-- или ROLLBACK при ошибке

```
**DQL/SELECT** дополнительно включает фильтрацию, группировку, сортировку, соединения и подзапросы:   
```
SELECT group_id, COUNT(*) AS student_count
FROM students
GROUP BY group_id
HAVING COUNT(*) > 20
ORDER BY student_count DESC;

```
Таблица для запоминания:   
|          Категория   <br> |                      Назначение   <br> |                                    Команды   <br> |
|:--------------------------|:---------------------------------------|:--------------------------------------------------|
|                DDL   <br> |                    структура БД   <br> |      `CREATE`, `ALTER`, `DROP`, `TRUNCATE`   <br> |
|                DML   <br> |                изменение данных   <br> |      `INSERT`, `UPDATE`, `DELETE`, `MERGE`   <br> |
|                DQL   <br> |                  выборка данных   <br> |                                   `SELECT`   <br> |
|                DCL   <br> |                   права доступа   <br> |                          `GRANT`, `REVOKE`   <br> |
|                TCL   <br> |                      транзакции   <br> | `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`   <br> |

Экзаменационный вывод: SQL является комплексным языком управления БД. Через DDL описывается структура, через DML и DQL выполняется работа с данными, через DCL защищается доступ, через TCL обеспечивается транзакционная согласованность.   
SQL делится на категории команд. DDL определяет структуру данных: `CREATE`, `ALTER`, `DROP`, `CREATE INDEX`, `CREATE VIEW`. DML изменяет строки: `INSERT`, `UPDATE`, `DELETE`, иногда `MERGE`. DQL отвечает за выборку, прежде всего `SELECT`. DCL управляет правами: `GRANT`, `REVOKE`. TCL управляет транзакциями: `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`.   
```
CREATE TABLE products (
    product_id integer PRIMARY KEY,
    name text NOT NULL,
    price numeric(10,2) CHECK (price >= 0)
);

INSERT INTO products(product_id, name, price)
VALUES (1, 'Клавиатура', 2500.00);
UPDATE products SET price = price * 1.1 WHERE product_id = 1;
DELETE FROM products WHERE product_id = 1;

SELECT name, price
FROM products
WHERE price > 1000
ORDER BY price DESC;

GRANT SELECT ON products TO analyst;
REVOKE UPDATE ON products FROM analyst;

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 500 WHERE account_id = 2;
COMMIT;

```
```
graph TD
    SQL[SQL] --> DDL[DDL: структура]
    SQL --> DQL[DQL: выборка]
    SQL --> DML[DML: изменение данных]
    SQL --> DCL[DCL: права]
    SQL --> TCL[TCL: транзакции]

```
Логический порядок обработки `SELECT`: `FROM`, `JOIN`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT`. Синтаксически `SELECT` стоит первым, но логически сначала определяется источник строк.   
Комплексный пример:   
```
SELECT d.name, AVG(er.grade) AS avg_grade
FROM exam_results er
JOIN disciplines d ON d.discipline_id = er.discipline_id
WHERE er.grade IS NOT NULL
GROUP BY d.name
HAVING AVG(er.grade) >= 4
ORDER BY avg_grade DESC;

```
SQL является декларативным языком: пользователь описывает результат, а СУБД выбирает план выполнения. Это отличает SQL от навигационных подходов, где программа сама задаёт маршрут обхода записей.

## 19. Методы обеспечения безопасности данных в БД   
### Конкретика для ответа   
**Безопасность данных в БД** — это совокупность мер, защищающих данные от несанкционированного доступа, изменения, уничтожения и раскрытия. Её нельзя сводить только к паролю пользователя: защита строится на нескольких уровнях.   
1. **Идентификация и аутентификация.** СУБД должна знать, кто подключается. Пользователь указывает логин, пароль, сертификат, Kerberos-токен или иной механизм. Пример: пользователь `app\_user` подключается к PostgreSQL с паролем или через сертификат.   
2. **Авторизация и разграничение прав.** После входа СУБД проверяет, какие действия разрешены. Пользователь может иметь право читать таблицу, но не изменять её.   
   
```
CREATE ROLE analyst LOGIN PASSWORD 'strong_password';
GRANT SELECT ON students TO analyst;
REVOKE INSERT, UPDATE, DELETE ON students FROM analyst;

```
1. **Принцип минимальных привилегий.** Каждому пользователю и приложению выдаются только те права, которые необходимы для работы. Веб-приложению не следует работать под суперпользователем БД.   
2. **Ролевое управление доступом.** Права назначают не каждому пользователю отдельно, а ролям: `analyst`, `teacher`, `admin`, `app\_service`. Это упрощает сопровождение.   
3. **Шифрование при передаче.** Соединение между клиентом и сервером должно быть защищено TLS/SSL, чтобы пароль и данные не передавались открытым текстом по сети.   
4. **Шифрование при хранении.** Данные могут шифроваться на уровне диска, файловой системы, tablespace, отдельных колонок или приложения. Особенно это важно для персональных данных, платёжной информации и документов.   
5. **Аудит.** Система должна фиксировать важные действия: входы, неудачные попытки доступа, изменение прав, удаление записей, изменение критических таблиц. Аудит нужен для расследования инцидентов.   
6. **Резервное копирование и восстановление.** Безопасность включает доступность. Если данные уничтожены ошибкой или атакой, должна быть возможность восстановить их из резервной копии.   
7. **Защита от SQL-инъекций.** Приложение должно использовать параметризованные запросы, а не склеивать SQL строками.   
   
Опасный пример:   
```
-- плохо: строка запроса склеивается с вводом пользователя
SELECT * FROM users WHERE login = '...';

```
Правильная идея: параметры передаются отдельно от текста запроса.   
Сводная таблица:   
|                                                          Угроза   <br> |                                       Мера защиты   <br> |
|:-----------------------------------------------------------------------|:---------------------------------------------------------|
|                               чужой пользователь читает таблицу   <br> |                           роли, `GRANT`, `REVOKE`   <br> |
|                                          перехват данных в сети   <br> |                                           TLS/SSL   <br> |
|                                                     кража диска   <br> |                               шифрование хранения   <br> |
|                                           ошибка администратора   <br> |                                   резервные копии   <br> |
|                                     вредоносный SQL через форму   <br> |                         параметризованные запросы   <br> |
|                                      незаметное удаление данных   <br> |                                             аудит   <br> |

Экзаменационный вывод: безопасность БД — это сочетание технических, организационных и программных мер. Надёжная система одновременно проверяет пользователя, ограничивает права, шифрует данные, пишет журнал действий и позволяет восстановиться после сбоя.   
Безопасность БД включает защиту от несанкционированного доступа, утечки, повреждения, уничтожения и злоупотребления правами. Она строится слоями: аутентификация, авторизация, шифрование, аудит, резервное копирование, сетевая защита, маскирование и контроль целостности.   
Аутентификация отвечает на вопрос «кто подключается». Используются пароли, сертификаты, Kerberos, LDAP и другие механизмы. Авторизация отвечает на вопрос «что разрешено». В SQL права выдаются ролям и пользователям через `GRANT` и отзываются через `REVOKE`.   
```
CREATE ROLE analyst LOGIN PASSWORD 'strong_password';
GRANT SELECT ON students TO analyst;
REVOKE INSERT, UPDATE, DELETE ON students FROM analyst;

```
Принцип минимальных привилегий требует выдавать только необходимые права. Приложение не должно подключаться под суперпользователем. Лучше иметь отдельные роли: чтение, запись, миграции, администрирование.   
Шифрование защищает данные при передаче и хранении. TLS/SSL защищает соединение клиент-сервер. Шифрование диска, файлов, резервных копий или отдельных столбцов защищает данные при компрометации носителя. При этом нужно защищать ключи: шифрование бесполезно, если ключ лежит рядом с данными в открытом виде.   
Аудит фиксирует важные действия: входы, ошибки доступа, изменение прав, чтение чувствительных данных, удаление и массовые обновления. Журналы помогают расследовать инциденты. Резервное копирование защищает от потери данных из-за ошибок, сбоев и атак. Backup нужно не только создавать, но и регулярно проверять восстановление.   
Маскирование и псевдонимизация нужны, когда разработчикам или аналитикам не требуются реальные персональные данные. Row-level security и column privileges позволяют ограничивать доступ к строкам и столбцам.   
```
graph TD
    S[Безопасность БД] --> A[Аутентификация]
    S --> P[Права и роли]
    S --> E[Шифрование]
    S --> L[Аудит]
    S --> B[Backup]
    S --> M[Маскирование]
    S --> I[Ограничения целостности]

```
Ограничения целостности тоже являются защитой: первичные ключи, внешние ключи, `CHECK`, `NOT NULL` предотвращают логическую порчу данных. Надёжная безопасность — это не один замок, а коридор шлюзов: пользователь проверяется, права ограничиваются, соединение шифруется, действия пишутся в журнал, а данные можно восстановить.

## 20. Обеспечение целостности реляционных баз данных   
### Конкретика для ответа   
**Целостность реляционной базы данных** — это свойство БД находиться в корректном, непротиворечивом состоянии относительно заданных правил предметной области и реляционной модели. Целостность обеспечивается не только приложением, но и самой СУБД через ограничения.   
Основные механизмы целостности:   
1. Первичный ключ (**`PRIMARY KEY`).** Гарантирует уникальность строк и запрещает `NULL` в ключевых атрибутах.   
```
CREATE TABLE groups (
    group_id integer PRIMARY KEY,
    group_name text NOT NULL
);

```
Нельзя создать две группы с одинаковым `group\_id`.   
2. Внешний ключ (**`FOREIGN KEY`).** Обеспечивает ссылочную целостность: значение в дочерней таблице должно существовать в родительской.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
Нельзя записать студента в группу `999`, если такой группы нет.   
3. Уникальность (**`UNIQUE`).** Запрещает повторение значений в одном или нескольких столбцах.   
```
ALTER TABLE students ADD CONSTRAINT uq_students_email UNIQUE(email);

```
4. Обязательность (**`NOT NULL`).** Запрещает отсутствие значения. Например, ФИО студента не должно быть пустым.   
5. Проверочные ограничения (**`CHECK`).** Задают допустимый диапазон или условие.   
```
CREATE TABLE marks (
    student_id integer REFERENCES students(student_id),
    discipline_id integer,
    mark integer CHECK (mark BETWEEN 2 AND 5)
);

```
**6. Ограничения предметной области.** Например, дата окончания обучения не может быть раньше даты поступления:   
```
CHECK (graduated_at IS NULL OR graduated_at >= enrolled_at)

```
**7. Транзакции.** Поддерживают согласованность при выполнении нескольких связанных изменений. Например, при удалении группы надо либо перенести всех студентов, либо запретить удаление.   
Варианты поведения внешнего ключа:   
```
FOREIGN KEY (group_id) REFERENCES groups(group_id)
ON DELETE RESTRICT
ON UPDATE CASCADE

```
`RESTRICT` запрещает удалить группу, если на неё ссылаются студенты. `CASCADE` может автоматически распространить изменение ключа. Использовать каскадное удаление надо осторожно, чтобы случайно не удалить важные зависимые данные.   
Экзаменационный пример нарушения целостности:   
|                                                                        Нарушение   <br> |                                                              Почему плохо   <br> |             Как запретить   <br> |
|:----------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------|:---------------------------------|
|                                                 две строки с одним `student\_id`   <br> |                                    студент не идентифицируется однозначно   <br> |             `PRIMARY KEY`   <br> |
|                                       студент ссылается на несуществующую группу   <br> |                                                         ссылка «в никуда»   <br> |             `FOREIGN KEY`   <br> |
|                                                                   оценка равна 8   <br> |                                                 нарушена шкала оценивания   <br> |                   `CHECK`   <br> |
|                                                                 ФИО равно `NULL`   <br> |                                                           неполная запись   <br> |                `NOT NULL`   <br> |

Вывод: целостность — это не косметическая проверка, а фундаментальное свойство реляционной БД. Если ограничения находятся в СУБД, они действуют для всех приложений одинаково и не зависят от добросовестности отдельного программиста.   
Целостность реляционной БД означает корректность, непротиворечивость и соответствие данных правилам предметной области. Она должна обеспечиваться самой СУБД, а не только приложением, потому что к базе могут обращаться разные программы.   
Структурная целостность требует соответствия таблиц, атрибутов, типов и ключей. Первичный ключ идентифицирует строку, `NOT NULL` запрещает отсутствие обязательного значения, типы данных не позволяют записать произвольную строку в дату.   
Ссылочная целостность требует корректности связей между таблицами. Внешний ключ не позволяет создать студента в несуществующей группе.   
```
CREATE TABLE groups (group_id integer PRIMARY KEY);
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
Доменная целостность ограничивает допустимые значения. Например, оценка от 2 до 5:   
```
CREATE TABLE exam_results (
    student_id integer,
    discipline_id integer,
    grade integer CHECK (grade BETWEEN 2 AND 5),
    PRIMARY KEY (student_id, discipline_id)
);

```
Семантическая целостность выражает бизнес-правила: нельзя оформить заказ без остатка товара, нельзя поставить оценку по дисциплине вне учебного плана, нельзя назначить преподавателя в две аудитории одновременно. Простые правила задаются `CHECK`, сложные — триггерами, процедурами, транзакциями и логикой приложения.   
Транзакционная целостность обеспечивает выполнение связанных операций как единого целого. Если заказ создан, позиции добавлены, остатки списаны и оплата проведена, всё это должно быть зафиксировано вместе или отменено вместе.   
```
graph TD
    I[Целостность] --> S[Структурная]
    I --> R[Ссылочная]
    I --> D[Доменная]
    I --> B[Семантическая]
    I --> T[Транзакционная]

```
При удалении связанных строк используются действия `ON DELETE RESTRICT`, `CASCADE`, `SET NULL`, `SET DEFAULT`. Выбор зависит от смысла. Для учебной системы удаление группы со студентами обычно запрещают, а не каскадно удаляют студентов.   
Нормализация также поддерживает целостность, потому что уменьшает дублирование. Если название группы хранится один раз в `groups`, оно не расходится в разных строках студентов. Итак, целостность обеспечивается ключами, ограничениями, доменами, транзакциями, нормализацией и бизнес-правилами.

## 21. Структурная, ссылочная, языковая и семантическая целостность   
### Конкретика для ответа   
В учебных пособиях по реляционным БД часто выделяют несколько видов целостности: структурную, ссылочную, языковую и семантическую. Их удобно различать по вопросу, на который они отвечают.   
**Структурная целостность** отвечает на вопрос: «Правильно ли данные организованы как реляционные отношения?». Она требует, чтобы таблицы имели строки и столбцы, строки были однотипными, атрибуты имели допустимые типы, каждая строка могла быть идентифицирована ключом. Пример нарушения: таблица `students` не имеет первичного ключа, а в одном поле `phones` хранится список телефонов через запятую. Это нарушает структурную строгость и атомарность.   
SQL-пример обеспечения структурной целостности:   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    birth_date date
);

```
**Ссылочная целостность** отвечает на вопрос: «Не ссылается ли запись на несуществующий объект?». Она обеспечивается внешними ключами. Пример: студент не может быть записан в группу, которой нет в таблице `groups`.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    group_id integer NOT NULL REFERENCES groups(group_id)
);

```
Если выполнить `INSERT INTO students VALUES (1, 'Иванов', 999)`, а группы 999 нет, СУБД должна отклонить операцию.   
**Языковая целостность** отвечает на вопрос: «Можно ли корректно обращаться к данным средствами языка БД?». Она связана с тем, что операции должны выполняться в рамках формального языка запросов и не должны нарушать структуру отношений. Например, запрос должен ссылаться на существующие таблицы и атрибуты, типы в выражениях должны быть совместимы, результат запроса должен быть корректным отношением.   
Пример языковой ошибки:   
```
SELECT unknown_column FROM students;

```
СУБД отклонит запрос, потому что атрибут не определён в схеме.   
**Семантическая целостность** отвечает на вопрос: «Соответствуют ли данные правилам предметной области?». Она задаётся ограничениями, триггерами, бизнес-правилами и иногда логикой приложения. Пример: оценка должна быть от 2 до 5, дата экзамена не может быть раньше даты начала семестра, сумма заказа не может быть отрицательной.   
```
CREATE TABLE marks (
    mark integer NOT NULL CHECK (mark BETWEEN 2 AND 5),
    exam_date date NOT NULL
);

```
Сравнение:   
|               Вид целостности   <br> |                                                                Смысл   <br> |                                                       Пример ограничения   <br> |
|:-------------------------------------|:----------------------------------------------------------------------------|:--------------------------------------------------------------------------------|
|                   Структурная   <br> |                                     корректная табличная организация   <br> |                                            `PRIMARY KEY`, атомарные поля   <br> |
|                     Ссылочная   <br> |                                 ссылки только на существующие строки   <br> |                                                            `FOREIGN KEY`   <br> |
|                      Языковая   <br> |                                       корректность операций языка БД   <br> |                                   существующие столбцы, совместимые типы   <br> |
|                 Семантическая   <br> |                                      соответствие предметной области   <br> |                                           `CHECK (mark BETWEEN 2 AND 5)`   <br> |

Экзаменационный вывод: структурная целостность описывает форму данных, ссылочная — связи между таблицами, языковая — корректность обращения к данным, семантическая — смысловые правила предметной области.   
Структурная целостность означает, что данные соответствуют структуре реляционной модели: таблицы имеют атрибуты, атрибуты имеют домены, строки идентифицируются ключами, значения соответствуют типам. Пример: `student\_id` является первичным ключом, `full\_name` не может быть `NULL`, `birth\_date` имеет тип даты.   
```
CREATE TABLE students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL,
    birth_date date
);

```
Ссылочная целостность означает корректность межтабличных ссылок. Если студент ссылается на группу, такая группа должна существовать. Это реализуется внешними ключами. При удалении родительской записи СУБД должна либо запретить удаление, либо выполнить заданное действие: cascade, set null, restrict.   
Языковая целостность означает, что операции с данными выполняются через разрешённые языковые средства СУБД и подчиняются их правилам. Пользователь не должен обходить SQL и напрямую править файлы таблицы, нарушая ключи и ограничения. Также языковые средства должны позволять задавать права, ограничения и транзакции.   
```
GRANT SELECT ON students TO analyst;
REVOKE DELETE ON students FROM analyst;

```
Семантическая целостность означает соответствие данных смыслу предметной области. Например, оценка должна быть от 2 до 5; дата окончания договора не раньше даты начала; студент не получает оценку по дисциплине, которую не изучал. Часть правил выражается `CHECK`, часть требует триггеров или процедур.   
```
CREATE TABLE practice (
    start_date date NOT NULL,
    end_date date NOT NULL,
    CHECK (end_date >= start_date)
);

```
```
graph TD
    C[Целостность БД] --> A[Структурная: типы, ключи, домены]
    C --> B[Ссылочная: внешние ключи]
    C --> L[Языковая: операции через SQL и права]
    C --> S[Семантическая: бизнес-правила]

```
База может быть структурно и ссылочно корректной, но семантически неверной. Например, все ключи существуют, но преподаватель одновременно назначен на две пары. Поэтому полноценная целостность требует сочетания всех видов: структура задаёт каркас, ссылки соединяют таблицы, язык контролирует операции, семантика делает данные правдивыми.

## 22. Содержание этапов проектирования базы данных   
### Конкретика для ответа   
Этапы проектирования базы данных — это последовательность работ от анализа предметной области до реализации и сопровождения схемы в конкретной СУБД.   
**1. Анализ предметной области.** Определяются цели системы, пользователи, документы, отчёты, операции и ограничения. Например, для учебной системы выясняют, что нужно хранить студентов, группы, дисциплины, преподавателей, оценки и ведомости.   
**2. Сбор требований.** Фиксируются функциональные требования: какие данные вводятся, какие отчёты формируются, какие запросы выполняются чаще всего. Также определяются нефункциональные требования: объём данных, число пользователей, требования к безопасности, резервному копированию, скорости работы.   
**3. Инфологическое проектирование.** Строится концептуальная модель: сущности, атрибуты, связи, кардинальности. Например, `Группа 1:N Студент`, `Студент M:N Дисциплина`.   
**4. Даталогическое проектирование.** Концептуальная модель преобразуется в логическую схему таблиц. Выбираются первичные ключи, внешние ключи, типы связей, таблицы для связей многие-ко-многим.   
**5. Нормализация.** Проверяются функциональные зависимости, устраняются избыточность и аномалии. Таблицы приводятся как минимум к 3НФ или BCNF, если это оправдано.   
**6. Физическое проектирование.** Выбираются конкретные типы данных, индексы, ограничения, партиционирование, настройки хранения. Например, `student\_id integer`, `full\_name varchar(200)`, индекс по `group\_id`.   
**7. Реализация.** Создаются SQL-скрипты: `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE`, ограничения, роли и представления.   
**8. Загрузка и проверка данных.** Выполняется импорт начальных данных, проверяются ограничения, тестируются основные запросы и отчёты.   
**9. Эксплуатация и сопровождение.** Проводятся резервное копирование, мониторинг производительности, обновление схемы, аудит доступа, оптимизация запросов.   
Схема:   
```
flowchart TD
    A[Анализ предметной области] --> B[Требования]
    B --> C[ER-модель]
    C --> D[Логическая схема таблиц]
    D --> E[Нормализация]
    E --> F[Физическая схема]
    F --> G[SQL-реализация]
    G --> H[Тестирование и эксплуатация]

```
Конкретный пример результата этапов:   
|                            Этап   <br> |                                                          Результат для учебной БД   <br> |
|:---------------------------------------|:-----------------------------------------------------------------------------------------|
|                          Анализ   <br> |                                        нужны студенты, группы, дисциплины, оценки   <br> |
|                       ER-модель   <br> |                                       студент принадлежит группе, получает оценки   <br> |
|                Логическая схема   <br> |                                      `students`, `groups`, `disciplines`, `marks`   <br> |
|                    Нормализация   <br> |                                               название группы вынесено в `groups`   <br> |
|                Физическая схема   <br> |                                             индексы по `group\_id`, `student\_id`   <br> |
|                      Реализация   <br> |                                                            SQL-скрипт создания БД   <br> |

Вывод: проектирование БД — это не только рисование таблиц. Это управляемый процесс, который начинается с понимания предметной области и заканчивается рабочей, защищённой и производительной схемой в СУБД.   
Проектирование БД начинается с анализа требований. Нужно выяснить, какие данные хранятся, кто ими пользуется, какие операции выполняются, какие отчёты нужны, какие есть ограничения безопасности, объёма и производительности. Для учебной системы выясняют правила групп, дисциплин, оценок, пересдач, ролей пользователей.   
Следующий этап — инфологическое проектирование. Строится концептуальная модель предметной области: сущности, атрибуты, связи, кардинальности, бизнес-правила. Результат — ER-диаграмма и текстовое описание.   
Далее выполняется даталогическое проектирование. Концептуальная модель переводится в логическую реляционную схему: таблицы, столбцы, первичные и внешние ключи, связи M:N через промежуточные таблицы. Затем схема нормализуется: устраняются повторяющиеся группы, частичные и транзитивные зависимости.   
Физическое проектирование адаптирует схему к конкретной СУБД: выбираются типы данных, индексы, партиционирование, схемы, роли, права, стратегия backup. Здесь учитываются реальные запросы и нагрузка.   
После этого выполняется реализация: SQL-скрипты, миграции, таблицы, ограничения, индексы, представления, функции, роли. Затем загрузка данных и проверка качества: дубли, отсутствующие справочники, неверные даты, нарушения внешних ключей.   
Тестирование проверяет типовые сценарии, ограничения, права, транзакции, производительность, планы запросов. Эксплуатация включает мониторинг, резервное копирование, восстановление, миграции, оптимизацию и сопровождение.   
```
graph TD
    A[Анализ требований] --> B[Инфологическая модель]
    B --> C[Даталогическая схема]
    C --> D[Нормализация]
    D --> E[Физическое проектирование]
    E --> F[Реализация]
    F --> G[Загрузка и проверка]
    G --> H[Тестирование]
    H --> I[Эксплуатация]
    I -. новые требования .-> A

```
Проектирование итерационно: новые требования могут вернуть к концептуальной модели, проблемы производительности — к физической схеме, ошибки данных — к ограничениям. Хороший ответ на экзамене должен раскрывать содержание этапов, а не просто перечислять названия.

## 23. Основные категории инструкций языка запросов SQL   
### Конкретика для ответа   
Основные категории инструкций SQL совпадают с функциональными частями языка. В ответе важно назвать категории, дать точное назначение и привести по 1–2 примера.   
**DDL — Data Definition Language.** Инструкции определения данных. Используются для создания и изменения объектов БД.   
```
CREATE SCHEMA education;
CREATE TABLE education.students (
    student_id integer PRIMARY KEY,
    full_name text NOT NULL
);
ALTER TABLE education.students ADD COLUMN email text;
DROP TABLE education.old_students;

```
DDL меняет структуру базы данных. После `CREATE TABLE` появляется новый объект схемы, после `ALTER TABLE` меняется структура таблицы.   
**DML — Data Manipulation Language.** Инструкции изменения данных. Они работают со строками таблиц.   
```
INSERT INTO education.students(student_id, full_name)
VALUES (1, 'Иванов Иван');

UPDATE education.students
SET email = 'ivanov@example.com'
WHERE student_id = 1;

DELETE FROM education.students
WHERE student_id = 1;

```
**DQL — Data Query Language.** Инструкции выборки. Главная команда — `SELECT`. Она может включать `WHERE`, `JOIN`, `GROUP BY`, `HAVING`, `ORDER BY`, подзапросы и агрегатные функции.   
```
SELECT g.group_name, COUNT(*) AS cnt
FROM students s
JOIN groups g ON g.group_id = s.group_id
GROUP BY g.group_name
ORDER BY cnt DESC;

```
**DCL — Data Control Language.** Инструкции управления правами.   
```
GRANT SELECT ON education.students TO analyst;
REVOKE SELECT ON education.students FROM analyst;

```
**TCL — Transaction Control Language.** Инструкции управления транзакциями.   
```
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;

```
Если нужно отменить изменения:   
```
ROLLBACK;

```
**SAVEPOINT** позволяет откатить не всю транзакцию, а её часть:   
```
BEGIN;
INSERT INTO orders(order_id) VALUES (10);
SAVEPOINT before_items;
INSERT INTO order_items(order_id, product_id) VALUES (10, 99);
ROLLBACK TO before_items;
COMMIT;

```
Итоговая таблица:   
|          Категория   <br> |           Назначение   <br> |                Основные команды   <br> |                              Что меняет   <br> |
|:--------------------------|:----------------------------|:---------------------------------------|:-----------------------------------------------|
|                DDL   <br> |            структура   <br> |       `CREATE`, `ALTER`, `DROP`   <br> |                                схему БД   <br> |
|                DML   <br> |               данные   <br> |    `INSERT`, `UPDATE`, `DELETE`   <br> |                           строки таблиц   <br> |
|                DQL   <br> |              выборка   <br> |                        `SELECT`   <br> |                    возвращает результат   <br> |
|                DCL   <br> |                права   <br> |               `GRANT`, `REVOKE`   <br> |                    доступ пользователей   <br> |
|                TCL   <br> |           транзакции   <br> |   `BEGIN`, `COMMIT`, `ROLLBACK`   <br> |                    состояние транзакции   <br> |

Экзаменационный вывод: SQL является не одним оператором `SELECT`, а полным языком управления реляционной БД: он описывает структуру, изменяет данные, выполняет запросы, управляет доступом и обеспечивает транзакционность.   
Категории SQL отражают полный жизненный цикл работы с базой. DDL создаёт и изменяет структуру: `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE INDEX`. DQL получает данные через `SELECT`. DML изменяет содержимое: `INSERT`, `UPDATE`, `DELETE`, `MERGE`. DCL управляет доступом: `GRANT`, `REVOKE`. TCL управляет транзакциями: `BEGIN`, `COMMIT`, `ROLLBACK`, `SAVEPOINT`.   
```
CREATE TABLE products (
    product_id integer PRIMARY KEY,
    name text NOT NULL,
    price numeric CHECK (price >= 0)
);
ALTER TABLE products ADD COLUMN is_active boolean DEFAULT true;

INSERT INTO products VALUES (1, 'Мышь', 1000, true);
UPDATE products SET price = 1100 WHERE product_id = 1;
DELETE FROM products WHERE is_active = false;

SELECT name, price FROM products
WHERE price > 500
ORDER BY price;

GRANT SELECT ON products TO analyst;
REVOKE UPDATE ON products FROM analyst;

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;

```
|          Категория   <br> |                    Назначение   <br> |                 Примеры   <br> |
|:--------------------------|:-------------------------------------|:-------------------------------|
|                DDL   <br> |                     структура   <br> |     CREATE, ALTER, DROP   <br> |
|                DQL   <br> |                       выборка   <br> |                  SELECT   <br> |
|                DML   <br> |               изменение строк   <br> |  INSERT, UPDATE, DELETE   <br> |
|                DCL   <br> |                         права   <br> |           GRANT, REVOKE   <br> |
|                TCL   <br> |                    транзакции   <br> | BEGIN, COMMIT, ROLLBACK   <br> |

```
graph LR
    DDL[DDL: структура] --> DML[DML: данные]
    DML --> DQL[DQL: запросы]
    DCL[DCL: права] --> DQL
    TCL[TCL: транзакции] --> DML

```
SQL декларативен: пользователь описывает требуемый результат или изменение, а СУБД выбирает физический план выполнения. Это поддерживает независимость данных и оптимизацию.

## 24. Нереляционные решения БД: key-value, документные, колоночные, графовые   
### Конкретика для ответа   
**Нереляционные БД (NoSQL)** — это класс систем хранения данных, которые не используют реляционную таблицу как единственный основной способ представления данных. Они появились как ответ на задачи горизонтального масштабирования, хранения полуструктурированных данных, высоких нагрузок и гибких схем.   
**Key-value БД** хранят данные как пары «ключ — значение». Ключ уникален, значение может быть строкой, JSON, бинарным объектом. Примеры: Redis, Riak, Amazon DynamoDB. Конкретный пример: ключ `user:1001`, значение `{"name":"Ivan","status":"active"}`. Такие БД быстры для операций `GET key` и `SET key value`, но плохо подходят для сложных запросов по множеству полей.   
```
user:1 -> {name: "Иван", city: "SPb"}
session:abc123 -> {user_id: 1, expires: "2026-06-03"}

```
**Документоориентированные БД** хранят документы, обычно в JSON/BSON-подобном формате. Пример: MongoDB, CouchDB. Документ может содержать вложенные структуры и массивы. Это удобно, когда объект естественно хранится целиком: профиль пользователя, заказ с позициями, карточка товара.   
```
{
  "student_id": 1,
  "full_name": "Иванов Иван",
  "contacts": {
    "email": "ivanov@example.com",
    "phone": "+79990000000"
  },
  "skills": ["SQL", "Python"]
}

```
**Колоночные БД** в NoSQL-смысле хранят данные по семействам колонок и оптимизированы для больших распределённых наборов данных. Примеры: Apache Cassandra, HBase. Они подходят для событий, телеметрии, логов и временных рядов, где важны высокая скорость записи и горизонтальное масштабирование.   
**Графовые БД** хранят данные как вершины и рёбра. Примеры: Neo4j, JanusGraph. Они удобны, когда главное — связи: социальные графы, рекомендации, маршруты, зависимости, fraud detection.   
```
CREATE (s:Student {name: 'Иванов'})-[:STUDIES]->(d:Discipline {name: 'Базы данных'});

```
Сравнение:   
|              Тип NoSQL   <br> |                  Единица хранения   <br> |                                          Сильная сторона   <br> |       Пример   <br> |
|:------------------------------|:-----------------------------------------|:----------------------------------------------------------------|:--------------------|
|              Key-value   <br> |                   ключ и значение   <br> |                             сверхбыстрый доступ по ключу   <br> |        Redis   <br> |
|            Документная   <br> |                     JSON-документ   <br> |                                 гибкая структура объекта   <br> |      MongoDB   <br> |
|             Колоночная   <br> |                 семейства колонок   <br> |                            большие распределённые записи   <br> |    Cassandra   <br> |
|               Графовая   <br> |                      узлы и рёбра   <br> |                                            анализ связей   <br> |        Neo4j   <br> |

Важно сказать: NoSQL не означает «SQL запрещён» или «реляционные БД устарели». Это набор альтернативных моделей, которые выбирают под конкретные требования. Если нужны строгие транзакции, сложные JOIN и нормализованная структура, часто лучше реляционная СУБД. Если нужны гибкие документы, граф связей или масштабируемое key-value хранилище, уместны NoSQL-решения.   
NoSQL-системы применяются там, где реляционная модель не всегда удобна: гибкая схема, горизонтальное масштабирование, полуструктурированные данные, высокие нагрузки записи, графовые связи. NoSQL лучше понимать как «not only SQL», а не как запрет SQL.   
Key-value БД хранят пары ключ-значение. Примеры: Redis, DynamoDB, Riak. Они хороши для кэшей, сессий, токенов, счётчиков, быстрых lookup-операций. Недостаток — слабые запросы по внутренней структуре значения.   
```
key: session:abc123
value: {"user_id": 10, "role": "student"}

```
Документно-ориентированные БД хранят JSON/BSON-документы. Примеры: MongoDB, CouchDB. Они удобны для профилей, заказов, каталогов, где объект естественно хранится целиком и может иметь вложенные поля.   
```
{
  "order_id": 100,
  "customer": {"id": 5, "name": "Иванов"},
  "items": [{"product_id": 10, "quantity": 2}],
  "status": "paid"
}

```
Колоночные wide-column БД хранят данные по семействам столбцов и проектируются под конкретные запросы. Примеры: Cassandra, HBase, ScyllaDB. Они подходят для телеметрии, журналов событий, временных рядов и распределённых нагрузок, но плохо заменяют произвольные SQL-соединения.   
Графовые БД хранят узлы и связи. Примеры: Neo4j, JanusGraph, Amazon Neptune. Они подходят для социальных сетей, рекомендаций, маршрутов, графов знаний, антифрода и анализа зависимостей.   
```
graph LR
    A((Person: Иван)) -- FRIEND_OF --> B((Person: Пётр))
    A -- BOUGHT --> C((Product: Ноутбук))

```
|                    Тип   <br> |                        Модель   <br> |        Примеры   <br> |                                          Лучше всего для   <br> |
|:------------------------------|:-------------------------------------|:----------------------|:----------------------------------------------------------------|
|              Key-value   <br> |               ключ → значение   <br> |          Redis   <br> |                                              кэш, сессии   <br> |
|            Документная   <br> |                 JSON-документ   <br> |        MongoDB   <br> |                                           гибкие объекты   <br> |
|             Колоночная   <br> |                   wide-column   <br> |      Cassandra   <br> |                            большие распределённые записи   <br> |
|               Графовая   <br> |                  узлы и связи   <br> |          Neo4j   <br> |                                             связи и пути   <br> |

NoSQL не отменяет реляционные СУБД. В реальных системах их часто комбинируют: PostgreSQL для транзакционных данных, Redis для кэша, MongoDB для гибких документов, Neo4j для рекомендаций. Выбор зависит от модели данных, запросов, целостности, масштабирования и транзакций.

## 25. Принцип хранения данных в графовой базе Neo4j. Пример модели   
### Конкретика для ответа   
Neo4j использует **property graph model**, то есть модель графа свойств. В ней данные представлены как **узлы**, **отношения**, **метки** и **свойства**.   
**Узел (node)** — объект предметной области. Например, студент, дисциплина, преподаватель, группа. Узел может иметь одну или несколько меток. Метка показывает тип объекта: `:Student`, `:Discipline`, `:Teacher`.   
**Отношение (relationship)** — направленная связь между двумя узлами. Отношение имеет тип: `STUDIES`, `TEACHES`, `BELONGS\_TO`. В Neo4j отношение всегда имеет начало и конец, но при запросе направление можно учитывать или игнорировать.   
**Свойство (property)** — пара «ключ — значение», хранящая данные узла или отношения. Например, у студента свойства `student\_id`, `full\_name`; у отношения `STUDIES` свойство `semester` или `mark`.   
**Путь (path)** — последовательность узлов и отношений. Например: студент → изучает → дисциплину → читается → преподавателем.   
Пример модели учебного процесса:   
```
flowchart LR
    S[Student: Иванов] -- STUDIES mark=5 --> D[Discipline: Базы данных]
    T[Teacher: Петров] -- TEACHES --> D
    S -- BELONGS_TO --> G[Group: 4311]

```
Cypher-пример создания графа:   
```
CREATE (s:Student {student_id: 1, full_name: 'Иванов Иван'})
CREATE (g:Group {group_id: 4311, name: '4311'})
CREATE (d:Discipline {discipline_id: 10, name: 'Базы данных'})
CREATE (t:Teacher {teacher_id: 5, full_name: 'Петров Петр'})
CREATE (s)-[:BELONGS_TO]->(g)
CREATE (s)-[:STUDIES {semester: 5, mark: 5}]->(d)
CREATE (t)-[:TEACHES]->(d);

```
Запрос: найти дисциплины студента Иванова:   
```
MATCH (s:Student {full_name: 'Иванов Иван'})-[:STUDIES]->(d:Discipline)
RETURN d.name;

```
Запрос: найти преподавателей, которые связаны со студентом через изучаемые дисциплины:   
```
MATCH (s:Student {full_name: 'Иванов Иван'})-[:STUDIES]->(d:Discipline)<-[:TEACHES]-(t:Teacher)
RETURN t.full_name, d.name;

```
Сравнение с реляционной моделью:   
|                                   Реляционная БД   <br> |                                           Neo4j   <br> |
|:--------------------------------------------------------|:-------------------------------------------------------|
|                               таблица `students`   <br> |                                 узлы `:Student`   <br> |
|                            таблица `disciplines`   <br> |                              узлы `:Discipline`   <br> |
|             таблица связи `student\_disciplines`   <br> |                          отношения `[:STUDIES]`   <br> |
|                                     внешний ключ   <br> |                               явное ребро графа   <br> |
|                                       SQL `JOIN`   <br> |                       обход графа по отношениям   <br> |

Преимущество Neo4j проявляется, когда запросы зависят от связей переменной длины: найти друзей друзей, кратчайший путь, рекомендации, цепочки зависимостей. В реляционной БД такие задачи требуют множества JOIN или рекурсивных запросов. В графовой БД связь является объектом первого класса, поэтому обход графа выражается естественно.   
Экзаменационный вывод: Neo4j хранит данные не в виде набора нормализованных таблиц, а как граф объектов и связей. Узлы описывают сущности, отношения описывают связи, свойства хранят значения, а Cypher позволяет искать шаблоны в графе.   
Neo4j использует модель property graph — граф свойств. Основные элементы: узлы, связи, свойства, метки, типы связей и пути. Узел представляет сущность: человека, студента, товар, город, организацию. Метка классифицирует узел: `Student`, `Teacher`, `Discipline`. Свойства узла — пары ключ-значение, например `name`, `age`, `email`.   
Связь соединяет два узла, имеет направление и тип: `FRIEND\_OF`, `TEACHES`, `PASSED`, `WORKS\_AT`. Связь тоже может иметь свойства. Например, оценка является свойством связи `PASSED`, потому что относится не только к студенту и не только к дисциплине, а к факту сдачи дисциплины студентом.   
Путь — последовательность узлов и связей. Работа с путями делает графовые БД удобными для рекомендаций, социальных графов, маршрутов и зависимостей.   
```
graph LR
    S((Student: Иванов)) -- BELONGS_TO --> G((Group: ИС-101))
    S -- PASSED {grade:5} --> D((Discipline: Базы данных))
    T((Teacher: Сидоров)) -- TEACHES --> D

```
Создание модели на Cypher:   
```
CREATE (s:Student {student_id: 1, full_name: 'Иванов Иван'})
CREATE (g:Group {group_id: 101, name: 'ИС-101'})
CREATE (d:Discipline {discipline_id: 10, name: 'Базы данных'})
CREATE (t:Teacher {teacher_id: 5, full_name: 'Сидоров С. С.'})
CREATE (s)-[:BELONGS_TO]->(g)
CREATE (s)-[:PASSED {grade: 5}]->(d)
CREATE (t)-[:TEACHES]->(d);

```
Запрос дисциплин и преподавателей студента:   
```
MATCH (s:Student {full_name: 'Иванов Иван'})-[p:PASSED]->(d:Discipline)<-[:TEACHES]-(t:Teacher)
RETURN d.name AS discipline, p.grade AS grade, t.full_name AS teacher;

```
|             Составляющая   <br> |                                      Определение   <br> |                                                                 Пример   <br> |
|:--------------------------------|:--------------------------------------------------------|:------------------------------------------------------------------------------|
|                     Узел   <br> |                        объект предметной области   <br> |                                                           `(:Student)`   <br> |
|                    Метка   <br> |                                       класс узла   <br> |                                                   `Student`, `Teacher`   <br> |
|                    Связь   <br> |                           направленное отношение   <br> |                                                        `-[:TEACHES]->`   <br> |
|                Тип связи   <br> |                                    имя отношения   <br> |                                                               `PASSED`   <br> |
|                 Свойство   <br> |                          значение узла или связи   <br> |                                                             `grade: 5`   <br> |
|                     Путь   <br> |                           цепочка узлов и связей   <br> |                                   студент → дисциплина → преподаватель   <br> |

В реляционной БД связь обычно прячется во внешнем ключе и раскрывается через `JOIN`. В Neo4j связь является объектом первого класса: она явно хранится, имеет тип, направление и свойства. Поэтому Neo4j особенно полезна там, где главный вопрос звучит не «какие строки подходят», а «как объекты связаны между собой».

## Контрольный чек-лист конкретики перед экзаменом   
Перед сдачей письменного ответа проверь каждый билет по четырём критериям:   
1. **Есть точное определение.** Например, не «индекс ускоряет», а «индекс — дополнительная структура данных, хранящая значения ключа и ссылки на строки для ускорения поиска».   
2. **Есть формальный признак.** Для 2НФ — полная функциональная зависимость от всего составного ключа; для BCNF — каждый детерминант является суперключом; для внешнего ключа — значение должно существовать в родительском отношении.   
3. **Есть предметный пример.** Студенты, группы, дисциплины, оценки, заказы, товары, счета — конкретика лучше абстрактного дыма.   
4. **Есть SQL, таблица или схема.** На письменном экзамене это выглядит убедительнее, чем сплошной текст.   
   
Короткая формула качественного ответа: **определение → механизм → пример → ограничение/исключение → вывод**. Такой порядок даёт ответу структуру и не позволяет расползтись в общие слова.
